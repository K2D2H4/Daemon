# 얼굴 — 데몬에게 외형을 주는 설계

- 작성 2026-08-25, 같은 날 에셋 제작 전체를 실측하여 개정
- 상태: 계획 승인 대기 (approved for planning)
- 브랜치: `claude/daemon-appearance-animation-8393b7`

미리 렌더한 짧은 영상 클립과, 그 클립을 **무엇이 고르는가**에 대한 설계다. 클립을
만드는 건 쉬운 쪽이고 어려운 쪽은 후자다. 산문보다 결정이 중요하다.

**이 문서의 절반은 하루치 측정으로 고쳐졌다.** 처음 쓴 판본에서 §1의 RMS 측정
위치, §3.4의 종료 판정, §4의 데이터 경로·비율·fps·생성 모델 권고가 전부 틀렸다.
틀린 내용은 지우고 무엇이 그것을 뒤집었는지 남겼다 — 다음 사람이 같은 자리에서
같은 추측을 하지 않도록.

근거 규칙: CONTRACTS 2(음성 지연 경로에 모델 호출 금지)·4(레이어링)·9(단일
프로세스)·12(툴 감사 행). 재사용: [admin 웹 설계](../../design/2026-08-07-m5-admin-web-design.md)의
"인증 없음 = 오리진을 증명할 수 없음 = 그런 경로를 만들지 않는다" 태도.

## 무엇이고 무엇이 아닌가

**이다.** 상시 떠 있는 앰비언트 존재감이자 음성 대화 중의 얼굴. 로컬호스트
페이지 하나(`/face`)를 앱 창으로 띄운다.

**아니다.** 립싱크가 아니다. 런타임 생성이 아니다. 아바타 커스터마이징 UI가
아니다. 네이티브 앱이 아니다. 립싱크는 §6에 Phase 2 후보로 조건과 함께 남겼다.

## 승인된 결정

| # | 결정 | 버린 것 |
|---|---|---|
| 1 | 앰비언트 + 대화 얼굴 둘 다. **지연 최소화가 최우선** | 데모/쇼케이스 전용 |
| 2 | 표정 = 결정론적 activity + **모델이 선언하는 mood** | 결정론만 / 코드 휴리스틱 |
| 3 | 입은 **RMS 진폭 기반**. 오디오는 브라우저로 보내지 않는다 | 립싱크 없음 / 진짜 립싱크 |
| 4 | 같은 서버의 **전용 `/face` 라우트**, 앱 창으로 띄움 | admin 안의 탭 / 네이티브 창 |
| 5 | 에셋은 **주인 소유**, `<data_dir>/face/`. 리포에 동봉하지 않음 | 기본 얼굴 동봉 / 폴백 |
| 6 | **허브-앤-스포크**: 모든 클립이 같은 중립 포즈에서 시작·종료 | 상태당 루프만 / N² 전이 클립 |

**런타임 생성은 불가능하다.** 생성 모델은 클립 하나에 수십 초~수 분이 걸린다.
클립은 전부 미리 렌더하고 브라우저가 preload한다. 따라서 지연 예산은 (1) 상태
신호가 브라우저에 닿는 시간, (2) 클립이 바뀌는 시간뿐이다.

- 음성 경로의 `sulky` / `curious` (§5)
- 아바타 교체 UI — 파일을 디렉토리에 넣는 것이 인터페이스다
- 여러 아바타 프로필
- 원격/비-로컬호스트 접근

## 1. 상태 모델

**축이 두 개고 성격이 다르다.**

| | 무엇 | 성격 | 클립 |
|---|---|---|---|
| `activity` | `idle / listening / thinking / speaking / working` | 지속 **상태** | 루프 |
| `mood` | `amused / sulky / curious` | 일회성 **이벤트** | 원샷 |
| `flourish` | 의미 없음 | 일회성 **이벤트** | 원샷 |

mood를 상태가 아니라 이벤트로 두는 것이 핵심이다. 기분에 시작·끝 시각을 붙이는
순간 "언제 풀리는가"라는 답 없는 질문이 생기고(타이머? 다음 턴? 화제 전환?)
전부 추측이 된다. 웃음은 상태가 아니라 일어나는 일이다. 그리고 이 데이터 모델이
결정 6의 애니메이션 모델과 같은 모양이다 — 루프 ← activity, 원샷 ← 이벤트.

**flourish는 세 번째 종류다.** 긴 `idle` 중 무작위 간격(40~120초)으로 재생되는
원샷이고, 트리거도 의미도 없다. 존재 이유는 하나 — **8초 루프는 20분쯤 보면
주기가 들킨다.** 1분에 한 번 다른 동작이 끼어들면 그 패턴이 무너진다. mood 원샷과
재생 기계장치를 공유하므로 추가로 필요한 코드는 무작위 타이머 하나뿐이다.

### 새 모듈 `daemon/face.py`

```python
Activity = Literal["idle", "listening", "thinking", "speaking", "working"]
Mood = Literal["amused", "sulky", "curious"]

@dataclass(frozen=True, slots=True)
class FaceState:
    activity: Activity
    level: float          # 0.0..1.0, speaking 중에만 의미 있음

@dataclass(frozen=True, slots=True)
class OneShot:
    clip: str             # mood 이름 또는 flourish 이름
```

버스 하나가 이 둘을 나른다. **daemon 안의 어떤 구현도 import하지 않는다**
(CONTRACTS 4). 발행자는 버스를 주입받고 `daemon/app.py`가 조립한다.

**구독자가 0명이면 발행은 비교 한 번이다.** 얼굴 창을 안 열어두면 기능 전체가
공짜다. 텍스트 전용 설치는 아무 비용도 내지 않는다.

**level은 버퍼링하지 않고 덮어쓴다.** 구독자별 "최신값 슬롯" 하나만 둔다. 큐를
쓰면 느린 구독자 뒤로 입 모양이 밀려 쌓이는데, **밀린 입 모양은 건너뛴 입 모양보다
훨씬 나쁘다.**

### 신호의 출처

| 신호 | 출처 | 이미 아는가 |
|---|---|---|
| `listening` | `voice/conversation.py` — 마이크 열림 + VAD가 주인 발화 판정 | 예 |
| `thinking` | 요청 전송 후 첫 오디오/토큰 전까지 | 예 |
| `speaking` | **`now < _playback_until`** (아래) | 예 |
| `working` | `tools/runner.py` — decide → execute 구간 | 예 |
| `idle` | 위 어느 것도 아님 | 예 |
| `level` | 재생되는 PCM의 RMS (아래) | 계산만 |
| `mood` | 모델이 선언 | **유일하게 새로 만드는 것** |

activity 다섯 개는 코드가 이미 알고 있는 사실이다. 새로 추론하는 것이 없어서
지연도 0이고 틀릴 수도 없다.

### `speaking`의 시작과 끝은 `_playback_until`이 정한다

**초판은 여기를 두 번 틀렸다.** 처음에는 "`voice/audio.py`의 `_drain`에서
`stream.write` 직전에 RMS를 재라"고 적었고, 종료는 "큐가 비고 350ms 디바운스"로
적었다. 둘 다 폐기한다.

**틀린 이유 1 — 그 코드는 macOS에서 실행되지 않는다.** `AudioIO` 구현이 둘이다:
`SoundDeviceAudio`(`voice/audio.py:106`)와 `VoiceProcessingAudio`
(`voice/apple_audio.py:138`). 그리고 `app.py:build_voice_audio`는 darwin에서
후자를 고른다 — 대화는 에코 캔슬링이 필요하고 PortAudio에는 그 경로가 없기
때문이다. 후자에는 `_drain`도 `stream.write`도 없다. `scheduleBuffer`로 엔진에
넘기고 끝이다.

**틀린 이유 2 — 디바운스는 추측이고, 정확한 값이 이미 있다.**
`voice/conversation.py:683`:

```python
seconds = size / (self._audio.playback_sample_rate * PLAYBACK_BYTES_PER_FRAME)
# Chunks queue behind each other, so playback ends after whatever is already
# queued - not `at + seconds`, which would forget the backlog.
self._playback_until = max(self._playback_until, at) + seconds
```

`_playback_until`은 **큐에 쌓인 오디오가 실제로 다 재생될 벽시계 시각**이고,
백로그까지 누적한다. 배럼-인 판정용으로 이미 있다.

**그래서 규칙은 하나다:**

> **`speaking`은 `now < _playback_until`인 동안 정확히 참이다.**

이 한 줄이 주인이 지적한 두 실패를 둘 다 불가능하게 만든다:

- **말을 안 하는데 입이 움직임** — `_playback_until`은 마지막 샘플이 스피커를
  떠나는 시각이다. 추측이 아니라 계산값이므로 초과 재생이 없다.
- **말하는데 입이 닫혀 있음** — 발화 중간에 큐가 순간 비어도 `_playback_until`은
  미래에 있으므로 `speaking`이 유지된다. 디바운스가 필요 없다.

provider의 생성 종료 신호도 이미 다룬다 — Gemini는 `generationComplete` /
`turnComplete`(`voice/gemini_live.py:1101`), OpenAI는 `response.done`
(`voice/openai_realtime.py:91`). "더 올 오디오는 없다"와 "큐가 다 비었다"의 조합이
완전한 종료 판정이다.

**level도 같은 시계를 쓴다.** RMS는 청크가 `play()`로 들어올 때 계산하되, 그
값을 **그 청크가 실제로 들릴 시각에 맞춰** 내보낸다 — `_playback_until`이 이미
계산하고 있는 그 시각이다. `play()` 시점에 그대로 내보내면 큐 깊이만큼 소리보다
앞서가고, 입이 먼저 움직인다.

**이렇게 두면 오디오 백엔드를 하나도 건드리지 않는다.** 두 구현을 각각 고치는
대신 그 둘 위에 있는 `conversation.py`의 시계를 쓰기 때문이다. 초판이 계획했던
`PortAudioIO.__init__(on_level=...)` 추가는 폐기한다 — 애초에 그 클래스 이름조차
존재하지 않았다.

### mood 태그는 기억에 닿지 않는다

텍스트 경로에서 모델이 응답 맨 앞에 태그를 붙이고, **함수 하나가 그것을 떼어낸다
— 전송 전에도, 마크다운에 쓰기 전에도.** 태그가 대화 로그에 남으면 recall이 그것을
다시 프롬프트에 실어나르고 결국 페르소나로 세탁된다. 태그가 없으면 mood 이벤트
없음(중립으로 되돌리지 않는다 — 되돌릴 상태가 없다).

## 2. 전송

**SSE 하나. `speaking` 중에만 흐른다.**

```
GET /face/stream    text/event-stream
```

세 종류가 한 스트림에 실린다 — activity 변화, 원샷 이벤트, level 틱. 앞의 둘은
일어날 때만, level은 말하는 동안에만 25Hz. 조용할 때는 소켓이 열려만 있고
트래픽이 0이다.

**WebSocket이 아닌 이유.** 브라우저→데몬 방향이 없어 단방향으로 충분하고,
결정적으로 **재접속이 브라우저에 내장**돼 있다. `daemon update`나 재시작 뒤에
얼굴 창이 알아서 다시 붙는다. WS면 그 로직을 직접 짜야 하고, 그 실패는 항상
"얼굴이 굳은 채로 남는" 쪽이다. 루프백에서 지연 차이는 없다(25msg/s × 40B ≈ 1KB/s).

**첫 이벤트는 변화가 아니라 스냅샷이다.** 없으면 재접속 직후 데몬이 말하는 중인데
얼굴은 idle에 앉아 있다.

**level은 전송 계층에서도 합친다.** 창이 가려져 소비가 느려질 때 밀린 값이 쌓이면,
창을 다시 봤을 때 입이 소리보다 몇 초 뒤처진 채 따라온다. 큐 없음.

**읽기 전용이고 부수효과가 없다.** admin이 오리진 게이트 때문에 툴 경로를 아예
만들지 않은 것과 같은 이유로, 여기도 "지금 무엇을 하는 중인가" 외에는 아무것도
나가지 않고 아무것도 들어오지 않는다. 대화 내용은 나가지 않는다 — activity 이름과
float 하나가 전부다.

**지연 예산:** 프로세스 안 발행 → 루프백 SSE 쓰기 = 이벤트 루프 한 틱, 1ms 미만.
실제로 느껴질 지연은 전송이 아니라 크로스페이드이고, 그것은 줄여야 할 지연이
아니라 일부러 넣는 것이다.

## 3. 페이지와 재생

자연스러움이 여기서 결정된다.

### 3.1 클립은 미리 로드하고 디코더까지 예열한다

12개 전부 `<video muted loop playsinline preload="auto">`로 겹쳐 쌓고 하나만
보이게 한다. 로드 직후 각각 한 번 `play()` 후 즉시 `pause()`하고 `currentTime = 0`
으로 되돌려 **첫 프레임을 디코드시켜 둔다.**

이걸 빼면 처음 전환되는 클립에서 검은 프레임이 한 번 번쩍한다. 예열은 페이지 열
때 한 번, 이후 비용 0.

**메모리 비용(붙들고 있는 디코드 프레임):** 1080×1620 = 프레임당 7.0MB, 12개
상주 **84MB**. 4K(3840×5760)로 갔다면 프레임당 88.5MB × 12 = **1.06GB**였다.
연산이 아니라 메모리가 벽이고, 그 벽은 1080이 아니라 4K에 있다.

### 3.2 크로스페이드는 **들어오는 요소만** 애니메이션한다

180ms. 컷(0ms)은 포즈가 같아도 조명·미세움직임 차이로 튀고, 400ms를 넘기면 두
얼굴이 겹친 게 인지된다(고스팅).

**그리고 어느 쪽을 페이드하는지가 시간보다 중요하다.**

> **들어오는 요소를 위에 놓고 그것의 opacity만 0→1로 애니메이션한다. 나가는
> 요소는 페이드가 끝날 때까지 opacity 1을 유지하고, 그 뒤에 숨긴다.**

양쪽을 동시에 페이드하면 두 레이어가 모두 반투명한 순간이 생기고 그 아래로 페이지
배경이 비쳐 **밝기가 꺼진다.** 초판은 "180ms 크로스페이드"만 적어두고 이걸 빼먹었고,
그래서 프리뷰를 그렇게 짰다가 주인이 idle 전환마다 깜빡임을 보았다. 컷보다 눈에
띈다.

**idle로 돌아갈 때만** 아웃고잉 클립이 루프 끝(=중립 포즈)에 닿을 때까지 최대
500ms 기다린다. 나머지 전환은 이미 사건이 일어났으니 즉시 가야 하지만, idle 복귀는
지금이어야 할 이유가 없는 유일한 전환이고 동시에 가장 자주 일어나는 전환이다.

전환 시 들어오는 클립은 `currentTime = 0`으로 되감고 `play()`가 resolve된 뒤에
표시한다. `play()` 직후 바로 표시하면 첫 프레임이 아직 페인트되지 않아 배경이
비친다(§4.5의 짧은 GOP가 되감기를 한 프레임 안에 끝내준다).

### 3.3 `idle`은 3종을 무작위로 갈아탄다

`idle1` `idle2` `idle3`. 루프가 끝날 때마다 **직전과 다른 것**을 무작위로 고른다.
8초 주기가 체감상 24초가 되어 패턴 감지가 훨씬 어려워진다.

**셋의 움직임이 같지 않다는 것을 알고 골라야 한다** — 실측: `idle1` 0.46,
`idle3` 0.70, `idle2` **4.77**. `idle2`만 뚜렷하게 살아 있고 나머지 둘은 주인이
"너무 정적"이라고 기각했던 클립(0.42)과 같은 수준이다. 균등 무작위면 3분의 2는
거의 멈춘 얼굴이 된다. 가중치나 선별은 주인이 실물을 보고 정한다.

### 3.4 입: `playbackRate`를 엔벨로프로 변조 (0.85 ~ 1.25)

RMS 원본은 너무 떨려 그대로 쓰면 입이 경련한다. **빠른 어택(~30ms) / 느린
릴리즈(~150ms)** 비대칭 엔벨로프를 씌운다 — 실제 입이 그렇게 움직인다.

범위를 조이는 이유: 0.8 아래는 슬로모션, 1.3 위는 배속으로 보인다. 둘 다 정확히
섬뜩함이 사는 곳이다.

**문장 중간 쉼(100~300ms)은 따로 처리하지 않는다.** 릴리즈가 알아서 느려지게
만들고 그것이 맞다 — 쉼표 하나에 입을 완전히 닫는 사람은 없다.

이 방식은 검증된 실용 해법이다. VTube Studio의 기본(Simple) 립싱크가 글자 그대로
`MouthOpen = VoiceVolume`이고, 프로 VTuber들이 몇 시간짜리 생방송을 그것으로 한다.
그 도구의 Advanced 립싱크는 A·I·U·E·O 비셈을 쓰는데, **우리는 그 단계에 갈 수
없다** — 크로스페이드가 180ms인데 음소는 80~150ms다. 리그는 파라미터를 즉시
모프하지만 비디오 클립은 못 한다. **비디오 클립으로는 엔벨로프까지고 음소는
원리적으로 불가능하다.**

### 3.5 `speaking`은 두 클립을 **임계값으로 전환**한다 (연속 블렌딩 아님)

`speaking_soft` / `speaking_loud`. 실측:

| | 개구량 중위값 | 최대 |
|---|---|---|
| `speaking_soft` | 15.0 | 31 |
| `speaking_loud` | 14.0 | **46** |

**중위값이 사실상 같고 최대만 48% 크다.** 즉 두 클립은 평소 발화에서 구분되지
않고 강조하는 순간에만 다르다. 그래서 엔벨로프로 연속 크로스페이드하면 거의 아무
효과가 없다. 측정에 맞는 방식은 **평소 `soft`, 엔벨로프가 상위 구간을 0.5초 이상
유지할 때만 `loud`로 전환**이다.

이 클립을 하나로 줄일지는 열어둔다. v1이 RMS를 이미 계산하므로 **실제 음성의
0.5초 창 엔벨로프를 기록하는 것이 공짜**다. 평평하면 `loud`를 버리면 된다.

### 3.6 원샷은 도착 즉시 재생하고, `speaking`이 자른다

텍스트 경로에서 mood 태그는 응답과 함께 오므로 원샷은 **말이 시작되기 직전**에
재생된다. 표정이 먼저 뜨고 말이 시작된다 — 사람이 하는 순서다.

말을 늦추지는 않는다. 오디오가 시작되면 원샷은 그 자리에서 `speaking`으로
크로스페이드되며 잘린다.

**flourish는 무작위 타이머로 재생된다** — `idle`이 40~120초 이어졌을 때. 어떤
activity 변화든 flourish를 즉시 자른다.

### 3.7 에셋이 없거나 일부만 있어도 동작한다

`<data_dir>/face/`가 비면 `/face`는 404가 아니라 **제작 안내(§4)**를 띄운다.
폴백 사슬은 하나뿐이다 — `working → thinking → idle`, `listening → idle`,
`speaking_loud → speaking_soft → idle`, 그리고 원샷은 없으면 **아무 일도 일어나지
않는다**(idle로 대체하지 않는다. 웃으라는 신호에 무표정한 루프를 트는 것은 표정이
없는 것보다 나쁘다).

### 3.8 곁다리

애니메이션 시간 계산을 `requestAnimationFrame`으로 하지 않는다. `<video loop>`
재생은 네이티브라 백그라운드 스로틀과 무관하지만 rAF는 스로틀된다. rAF는
`playbackRate` 갱신에만 쓴다 — 스로틀되면 덜 자주 갱신될 뿐 어긋나지 않는다.

페이지는 admin처럼 자족형 HTML 한 장, 크롬 없는 단색 배경.
`daemon face`가 `--app=http://127.0.0.1:PORT/face`로 연다. **배경색은 클립에서
샘플링한 값을 쓴다** — 클립을 색에 맞추는 게 아니라 페이지를 클립에 맞추는 쪽이
쉽고 정확하다. 현재 에셋의 측정값은 `#19191B`.

## 4. 에셋 — 실제로 만들어진 것

### 4.1 위치와 프레이밍

```
<data_dir>/face/            # DAEMON_DATA_DIR, 기본 ./data — `~/.daemon`이 아니다
  base.PNG                  # 2160x3840 4K 마스터, 보관
  base_2x3.png              # 1080x1620, Kling 입력. crop=2160:3240:0:200 + lanczos
  clips/                    # 생성 원본 (1176x1764, 24fps, 오디오 포함)
  *.mp4                     # 처리 완료본 (1080x1620, 24fps, 무음, GOP 12)
```

**2:3 세로, 1080×1620, 명치 바로 아래까지, 손은 정지 이미지에서 프레임 밖.**

**받아들인 대가 — 얼굴이 작아진다.** 400pt 창(=800px)에 띄우면 얼굴 폭이 가슴 위
프레이밍의 ~296px에서 **~207px**로 준다. **해상도로는 메울 수 없다** — 소스를
올려도 창 크기가 같으면 표시 픽셀은 같다. 얼굴을 키우는 방법은 창을 키우는 것뿐이고,
그것은 돈이 아니라 모니터 자리를 내는 일이다. 207px면 깜빡임·입 움직임·고개
갸웃은 충분히 읽히고 잃는 것은 피부 질감이다. 주인이 알고 선택했다.

**비율은 크롭으로 얻는다.** 기준 이미지를 2:3으로 재생성하면 시드가 바뀌어 얼굴을
잃는다. 4K 9:16 원본을 크롭하면 정체성이 정확히 보존된다. 그리고 **Kling은 입력
이미지의 비율을 따른다** — 2:3 이미지를 넣으니 2:3(1176×1764)이 나왔다. 초판은
"표준 비율만 지원할 것"이라고 추측했고 그것은 틀렸다.

### 4.3 제작의 핵심 제약과 그 대가

> **모든 클립은 같은 중립 포즈에서 시작해서 같은 중립 포즈로 끝난다.**

이 한 줄이 N² 전이 클립을 불필요하게 만든다. 그리고 **Kling의 Start & End Frames로
강제할 수 있다** — 시작·끝 프레임에 같은 `base_2x3.png`를 넣으면 프롬프트로
부탁하는 게 아니라 제품 기능이 보장한다. 실측 이음매 **1.09 ~ 1.22** (12개 전부).

**그러나 이것은 순이득이 아니다.** 8초 안에 정확히 같은 포즈로 돌아와야 한다면,
그것을 만족시키는 가장 값싼 방법은 **아예 안 움직이는 것**이다. 실측 결과 12개 중
9개가 앞이나 뒤에 정지 구간을 가졌고, `speaking` 두 개는 **마지막 2.12초 동안 입이
완전히 멈췄다.** 발화 시간의 26%다 — 주인이 방지하고 싶다고 한 "말하는데 입이
안 움직인다"가 정확히 이것이다.

**그래서 얼어붙은 앞뒤를 잘라내는 것은 선택이 아니라 필수 후처리다.** §4.5에
명령이 있다.

### 4.4 프롬프트

기준 이미지 (한 번만, GPT/Nano Banana 계열):

```
Upper body portrait of a woman in her mid-to-late twenties.
Long light blonde hair, bright blue eyes, fair skin.
Wearing a fitted sleeveless turtleneck in deep muted forest green.
Curvy figure. Confident, aloof, composed. Slightly haughty.
Framed from just below the solar plexus up. Arms visible, hands out of frame.
Completely neutral, relaxed resting expression. Mouth closed. Not smiling.
Looking straight at the camera.
Plain flat solid background, no texture, no gradient, no props.
Even soft frontal lighting, no hard shadows.
Photorealistic, sharp focus on the face, natural skin texture.
```

**생성 모델 권고를 철회한다.** 초판은 Higgsfield Soul 2.0을 먼저 쓰라고 했고
근거는 "같은 플랫폼이라 영상 입력이 된다"였다. 둘 다 틀렸다 — Higgsfield
image-to-video는 **아무 이미지나 업로드받으므로** 같은 플랫폼일 이유가 없고,
주인의 실측으로 Soul은 "너무 현실적이라 오히려 못생겨 보임"이었다. **GPT 계열이
이겼다.** 실사 특화 모델은 지시를 "예쁘게" 해석하는 편향이 있어 제약 많은
프롬프트에 불리하다. Soul ID는 20장 이상의 학습 이미지를 요구해 존재하지 않는
인물에겐 순환이고, §4.3이 "1장을 재사용"으로 정체성 문제를 이미 구조적으로 푼다.

**의상 색이 배경과 붙으면 안 된다.** 검정 상의는 명도가 배경과 같고 채도도 0이라
몸통이 배경에 먹혀 머리와 어깨만 뜬다 — 상반신을 보여주려는 목적과 정면으로
어긋난다. 깊은 녹색을 채택한 이유는 둘이다: 금발·벽안과 차가운 톤이 맞고,
**4:2:0 크로마 서브샘플링이 채도 높은 빨강 계열을 가장 심하게 뭉갠다**(§4.5가
`yuv420p`를 쓴다). 어느 쪽이든 `muted`를 넣는다.

**`Not smiling`을 빼지 않는다.** 기준 이미지가 곧 중립 포즈의 정의이고 12개 클립이
전부 여기서 시작해 여기로 돌아온다. 웃는 기준 이미지를 잡으면 `sulky`가 웃다가
삐치고 다시 웃는 것으로 끝난다. 다행히 **도도한 인상은 중립 포즈로 이상적이다** —
표정을 짓지 않으면서 표정이 있는 상태라, 무표정 기준 이미지가 밋밋해지는 문제가
사라지고 `amused`와의 대비도 커진다.

#### 클립 프롬프트의 원칙 — 네 번 데이고 얻은 것

> **원하는 세기보다 한 단계 낮춰 쓰고, 넘지 말아야 할 선을 부정문으로 명시한다.**

**감정 단어와 강조 표현은 이 모델에서 항상 과장된다.** 실제로 겪은 네 번:

| 쓴 표현 | 나온 것 |
|---|---|
| `nothing happens` | idle이 완전히 얼어붙음 (움직임 0.42) |
| `energy and emphasis` + `opening wide` + `head moving more` | 고함 |
| `pouts` | 입술을 오리처럼 모은 포즈 — 감정이 아니라 립 모양 |
| `bursting into a warm laugh` + `shoulders shaking` | 폭소, 얼굴이 일그러짐 |

**그리고 움직임은 세어서 지시해야 한다.** `occasional blink`는 무시당했고
`blinking naturally two or three times`는 작동했다. "가만히 있음"은 하나의 움직임이
아니라 서로 무관한 작은 움직임 여러 개이므로 각각을 따로 이름 붙인다 — 호흡,
깜빡임, 고개 기울임, 체중 이동, 머리카락 정착, 시선 드리프트.

**호흡은 `chest`가 아니라 `shoulders`로 지시한다.** 흉부의 부피 변화는 모델이
표현하기 어려운 3D 신호인데, 어깨의 위치 변화는 눈에 보인다. 사람도 남의 호흡을
알아볼 때 어깨를 본다.

모든 클립에 붙는 고정 꼬리:

```
static camera, no pan, no zoom, no camera movement.
same lighting, same background, same clothing, same framing.
returns to the exact starting pose and expression at the end.
```

정적 카메라를 명시하지 않으면 크로스페이드 시점마다 구도가 어긋난다. 실측
드리프트 **0.48 ~ 0.82** — 세 줄이 실제로 작동한다. 그리고 그 셋이 작동하므로
**모션 강도를 올려도 카메라는 안 움직인다.** 초판이 "강도 최저"를 권한 것이 idle을
얼린 원인 중 하나였다.

#### 손 규칙 — 좁혀진 형태

정지 이미지의 손과 영상의 손은 다른 문제다. image-to-video는 손이 **어떻게
움직이는지**를 새로 만들어야 하고, 그것은 클립당 프레임 200~300개 각각의 기회다.
그런데 실측 결과 이 모델·이 기준 이미지에서는 **팔과 손이 깨끗하게 나왔다.** 그래서
규칙이 "손 품질"에서 **"제스처 반복"**으로 바뀐다:

| | 허용 | 이유 |
|---|---|---|
| **루프** | **연속적인** 팔·손 움직임. **개별적인** 제스처는 금지 | 시작과 끝이 뚜렷한 제스처는 8초마다 반복되면 틱이 된다. "8초마다 턱을 만지는 사람". 반대로 말할 때 손짓처럼 끊김 없이 흐르는 움직임은 루프에서 안 들킨다 |
| **원샷** | 전부 | 반복이 없으니 개별 제스처의 자리다 |

`working`은 이 규칙의 **의도된 예외**다. 폰 확인은 개별 제스처지만, 툴 호출은 보통
몇 초라 루프가 한 바퀴도 못 돌고 끝나고, 반복되는 경우에도 **오래 걸리는 것을
기다리며 폰을 또 확인하는 것은 실제로 기다리는 사람이 하는 행동**이다. 틱이 아니라
상황 묘사가 된다.

**프롭은 프레임 밖에서 들어와야 한다.** 기준 이미지에 폰이 없으므로 화면 안에서
생겨나면 형태가 뭉개진다. `her hand rises into frame holding a phone` /
`lowers it out of frame`처럼 경계를 넘게 쓴다. 그리고 **명치 아래 프레이밍은 팔을
보여주므로, 영상 모델이 말하는 동작에 어울리는 제스처를 만들려고 손을 프레임 안으로
올린다** — 기준 이미지에 손이 없어도 일어난다. 원치 않는 클립에는
`hands stay out of frame, no gestures`를 명시한다.

### 4.5 인코딩과 필수 후처리

**H.264 MP4, 소스 fps 유지(24), 키프레임 간격 0.5초(`-g 12`), 오디오 없음,
1080×1620 정규화.**

VP9/WebM이 아닌 이유: 디코더 12개를 항상 물고 있으므로 하드웨어 디코드가 확실한
코덱이어야 한다. H.264는 macOS의 모든 브라우저에서 하드웨어 디코드된다.

**fps를 30으로 올리지 않는다.** 초판은 30을 적었으나 생성 결과가 24였고, 올리려면
프레임을 복제하거나 보간해야 해서 둘 다 손해다. 소스에 맞추고 GOP를 `fps/2`로 둔다.

짧은 GOP가 중요한 이유: 전환할 때 `currentTime = 0`으로 되감는데, 키프레임이
드물면 되감기가 한 박자 늦는다.

**필요 없었던 것 둘 (실측):**

- **디노이즈 불필요.** 배경 프레임간 변화 실측 **0.08 ~ 0.21** — 그레인이 기어다니지
  않는다. 4K로 생성해 Lanczos로 다운스케일한 것이 이유일 것이다(다운스케일이
  로우패스 필터로 작동해 고주파 그레인을 상쇄한다). `hqdn3d`를 걸 이유가 없다.
- **루프 클립의 크로스디졸브는 트림하지 않은 클립엔 불필요.** Start & End Frames가
  이음매를 1.09~1.22로 닫아준다. **트림한 클립에는 필요하다** — 맞물리던 프레임을
  잘라냈으므로.

**얼어붙은 앞뒤 트림 + 정규화 (루프, 트림했으므로 재봉합 포함):**

```bash
IN=clips/listening.mp4; OUT=listening.mp4; HEAD=0.00; TAIL=1.50; X=0.3
ENC="-an -c:v libx264 -pix_fmt yuv420p -r 24 -g 12 -crf 18 -movflags +faststart"
D=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$IN")
END=$(python3 -c "print($D - $TAIL)")
ffmpeg -v error -ss $HEAD -to $END -i "$IN" -vf "scale=1080:1620:flags=lanczos" $ENC -y /tmp/t.mp4
D2=$(ffprobe -v error -show_entries format=duration -of csv=p=0 /tmp/t.mp4)
OFF=$(python3 -c "print(max(0.0, $D2 - 2*$X))")
ffmpeg -v error -i /tmp/t.mp4 -filter_complex \
"[0:v]trim=start=${X},setpts=PTS-STARTPTS[body];\
 [0:v]trim=start=0:end=${X},setpts=PTS-STARTPTS[head];\
 [body][head]xfade=transition=fade:duration=${X}:offset=${OFF}[v]" \
 -map "[v]" $ENC -y "$OUT"
```

결과물의 첫 프레임과 마지막 프레임이 모두 트림본 `t=X` 시점의 프레임이 되어 루프가
이어진다. **원샷은 재봉합하지 않는다** — 루프가 아니므로 트림만 한다.

**주의(zsh):** 필터 문자열 안에서 `$OFF[v]`는 배열 첨자로 해석된다. `${OFF}[v]`로 쓴다.

**9:16으로 뽑았다면 2:3으로 크롭(상단 정렬 — 머리를 지키기 위해):**

```bash
ffmpeg -i raw.mp4 -vf "crop=iw:iw*3/2:0:0" -an cropped.mp4
```

### 4.6 비용 (참고, 2026-08 기준)

Higgsfield 플랜은 Starter $19(270크레딧) / Plus $59(1,200) / Ultra $129(3,000),
월 크레딧 이월 없음. 크레딧 팩은 80개 $5 ~ 1,700개 $80. 영상은 Seedance 2.0 기준
5초 1080p ≈ 45크레딧. **수치는 3rd-party 정리 글에서 온 것으로 서로 어긋난다.**

영상 모델은 **Kling 2.5 Turbo**를 썼다. 선택 기준이 화질이 아니라 **Start & End
Frames 지원**이었다는 점이 중요하다 — 모델 비교 글들은 "얼마나 시네마틱한가"로
순위를 매기는데, 우리에게 그것은 감점 요인이다. 우리가 원하는 것은 얌전하고
지루한 모델이다. Seedance 2.0은 "멀티샷 영화·광고"용으로 튜닝되어 부적합했다.

**진짜 비용 동인은 클립 수가 아니라 재시도율이고, 재시도의 원인은 대부분
프롬프트의 세기 조절이었다**(§4.4의 네 번). Start & End Frames가 포즈 복귀
문제를 없앤 뒤에는 남은 재시도가 전부 표정 강도 문제였다.

## 5. 음성 경로의 mood — v1에서는 넣지 않는다

### 문제

텍스트 경로는 쉽다 — 모델이 태그를 붙이고 우리가 뗀다. **음성엔 우리가 손댈
텍스트가 없다.** 오는 것은 오디오·트랜스크립트·툴 콜뿐이고, 트랜스크립트에 태그를
넣게 하면 그것을 소리 내어 읽는다.

### 툴로 받는 것이 답처럼 보이지만 CONTRACTS 12가 막는다

`set_mood(mood: string)`은 flat 스키마라 음성이 실제로 호출할 수 있다 —
`delegate_task`가 증명했듯 nested만 위조되고 flat은 된다
([async-delegation 설계](2026-08-14-async-delegation-design.md)).

그러나 CONTRACTS 12는 실행된 툴 콜이 전부 `tool_calls` 감사 행을 남기게 하고, 그
행의 목적을 "주인의, 무엇이 이 기계를 건드렸는지에 대한 ground-truth 기록"이라고
명시한다. **기분이 바뀐 것은 기계를 아무것도 건드리지 않았다.** 매 턴 mood 행이
쌓이면 `run_command`·`write_file` 행이 그 밑에 묻힌다.

**이것은 계약이 막는 게 아니라 "mood는 툴이 아니다"라고 알려주는 것이다.** 감사
행을 건너뛰는 예외는 계약이 "필요하면 멈추고 알려라"라고 적어둔 바로 그 상황이다.

### v1 결정

음성 중에는 **activity 4종 + level만** 흐른다. 정직하게: **음성 대화 중에는 웃음도
삐침도 나오지 않는다.** 손실이지만 실제로는 적다 — 음성 대화의 대부분 시간은 저
4개 중 하나이고, 입이 소리 따라 움직이고 몸이 기울고 시선이 움직이는 것만으로
존재감의 대부분이 나온다.

### 첫 후속: 웃음은 오디오에서 검출할 수 있다

결정 2에서 "코드가 감정을 추측"하는 것을 버렸는데, 그것은 **텍스트에서 단어로
감정을 추론**하는 것이었고 측정에서 실패했다(`MEASURED.md`: 주인 발화 463개에 감정
렉시콘 매치 0개).

**데몬 자신이 낸 소리에서 웃음을 잡는 것은 다른 종류다.** 감정을 추론하는 것이
아니라 웃음이라는 사건이 일어난 것을 관측하는 것이다. 웃음소리는 4~7Hz의 주기적
에너지 버스트로 음향적 특징이 뚜렷하고, **우리는 이미 RMS를 계산한다.** 새 툴 없음,
새 모델 호출 없음(CONTRACTS 2 유지), 감사 행 없음, 계약 변경 없음.

**데이터 없이 임계값을 튜닝하지 않는다.** v1은 음성 턴 동안 엔벨로프를 기록해두는
것이 공짜다. **v1이 v2를 결정할 데이터를 스스로 모은다.** 숫자는 `MEASURED.md`에
남긴다. `sulky`와 `curious`는 오디오로 잡히지 않으므로 `set_mood`로 가야 하고,
그것은 **CONTRACTS 12 변경 논의를 먼저 여는 것**이 전제다.

## 6. Phase 2 — 진짜 립싱크 (MuseTalk). 1·2단계 통과, 남은 것은 CONTRACTS 9

**초판은 "실시간 스트리밍 오디오에는 립싱크가 구조적으로 불가능"이라고 적었다.
그것은 과했다.** MuseTalk 같은 프레임 단위 latent 인페인팅 모델은 완성된 오디오
파일을 요구하지 않는다. 그 주장은 배치형 파이프라인에만 맞았다.

### 결론 먼저 (측정 2026-08-25/26, M4 Max 36GB, 우리 클립과 한국어 음성)

| 제약 | 요구 | 측정 | |
|---|---|---|---|
| 입 선명도 | 이질감 없을 것 | 원본의 **87% / 80%** | 통과 |
| 지연 | ≤ 250ms | **191ms** | 통과, 59ms 여유 |
| 처리량 (실제 듀티) | 24fps 유지 | **10/10 버스트, 드리프트 −0.5%**. 단 whisper 포함 시 24.6fps로 여유 2.5% | 통과, 선 위 |

**구성은 MLX UNet batch 2 + TAESD 디코더이고, 그 두 부품이 다 필요하다.** 아래에
각각 왜 필수인지 적는다. 선명도는 라플라시안 분산으로 입 영역만 재고 원본과 비교한
값이다(전체 프레임 평균은 §「에셋 QA」가 말한 대로 거짓 음성을 낸다).

### 0단계 정정 — 필요한 미래 오디오는 100ms가 아니라 **80ms**다

0단계는 `musetalk/whisper/audio2feature.py`를 읽었고 그것은 **v1.0 경로**다. 출시할
v1.5는 `musetalk/utils/audio_processor.py`를 쓰는데, 그 `get_whisper_chunk`는 특징
배열의 앞을 `ceil(50/fps) × padding_left` = 24fps에서 **6인덱스** 패딩한다. 200ms
총량은 그대로이고 분할이 옮겨간다 — **과거 120ms / 미래 80ms** (v1.0은 80/100).

인덱스 산술을 네 지점에서 측정한 정상 상태:

```
프레임  24: 미패딩 idx [44, 53]     오디오 1080.0ms까지 필요   프레임 시작 1000.0ms  → 80.0ms
프레임 100: 미패딩 idx [202, 211]   오디오 4240.0ms까지 필요   프레임 시작 4166.7ms  → 73.3ms
프레임 600: 미패딩 idx [1244, 1253] 오디오 25080.0ms까지 필요  프레임 시작 25000.0ms → 80.0ms
```

**0단계의 추론은 옳았고 결론도 바뀌지 않는다.** `(N, 50, 384)`의 50이 timestep이 아니라
Whisper 인코더 레이어 5개라는 읽기가 맞았고, 그래서 실제 시간 윈도는 200ms뿐이다.
20ms는 유리한 방향으로 움직였고, 예산을 ms 단위로 인용하는 곳이 있으므로 적어둔다.

부수 소득 둘도 그대로다. **24fps 그대로 써도 된다**(오차가 누적되지 않아 최대 양자화
오차 1 인덱스 = 20ms, 클립 12개를 다시 뽑지 않아도 된다). 그리고 **경계에서 안전하게
열화한다**(클램프로 엣지 특징을 반복).

그리고 **0단계의 답이 프레임워크와 무관하다는 판단도 맞았다** — 80ms는 모델 구조의
성질이라 백엔드를 바꿔도 줄지 않았다. 그래서 그것을 맨 앞에 두는 것이 옳았다.

### 1단계 — 가장 큰 항은 UNet이 아니라 **VAE 디코더**였다

batch-1 fp16 내역: UNet **44.47ms**, VAE 디코드 **48.16ms**. **디코드가 55%다.** 그리고
MuseTalk이 디코드에 쓰는 것은 특별한 것이 아니라 SD 1.x의 평범한 `sd-vae-ft-mse`다.
같은 4채널 잠재 공간에 대한 경량 대체품 `madebyollin/taesd`(9.8MB)로 바꾸면:

| | sd-vae-ft-mse | taesd |
|---|---|---|
| 디코드 지연 | 48.16ms | **5.09ms** (9.5배) |
| 입 영역 PSNR | — | 36.01 dB |
| 프레임간 RMSE (609프레임) | 8.19 | **7.89** |

색 편차는 채널당 게인 `[0.997, 0.985, 1.003]`(BGR) — 초록이 1.5% 낮고 나머지는 0.3%
안이며, 상수 게인 하나를 한 번 보정해 넣으면 입 영역 PSNR이 36.0 → 37.0dB로 회복된다.
프레임간 RMSE가 오히려 3.6% **낮으므로 깜빡임이 늘지 않는다**(정지 프레임 비교로는
답이 나오지 않는 항목이라 전체 렌더로 확인했다).

**이것은 최적화가 아니라 필수 부품 교체다.** 디코드 한 항(48.16ms)이 24fps 프레임
예산 전체(41.67ms)보다 크므로, TAESD 없이는 **어떤 백엔드에서도 24fps가 산술적으로
불가능하다.** UNet이 공짜여도 미달이다.

**붙여넣기는 벽이 아니었다.** MLX 모델 카드가 "얼굴 검출·크롭·블렌딩은 CPU"라고 적어
1.75MP 합성이 위험으로 보였으나 둘 다 해제된다. 검출과 마스크 생성은 고정 클립
루프에서는 **준비 단계**다(클립당 한 번, 오프라인). 그리고 프레임별 블렌드가 비싼 것은
구현 탓이다 — `get_image_blending`은 1080×1620 프레임 전체를 PIL로 두 번 왕복시켜
19.37ms를 쓰는데, 590×590 크롭박스만 numpy로 합성하면 **픽셀이 동일한 출력**(평균
절대차 0.0, 최대 0, 다른 픽셀 0개)을 **2.42ms**에 낸다.

**확대 아티팩트는 존재하지 않는다.** 실제 얼굴 박스가 **320×404px**이므로 모델에
256×256을 먹이는 것은 완만한 *축소*다(가로 0.80배, 세로 0.63배). 초판이 걱정한 방향과
반대다.

**"1단계에서 fps가 느린 것은 기각 사유가 아니다"는 판단도 맞았다.** PyTorch+MPS
batch-1은 98.6ms/프레임(10.1fps)이었고, 같은 M4 Max에서 ONNX+CoreML로 포팅한 제3자
측정도 11~12fps다 — 두 독립 구현이 같은 자리에 떨어지므로 그 숫자는 구현의 성질이지
모델의 한계가 아니다.

### 2단계 — MLX 포팅에는 새 파이프라인이 필요 없다

`mlx-community` 저장소는 여전히 가중치뿐이고 `musetalk_mlx`는 공개되지 않았다(PyPI
404, HF 저장소 파일은 safetensors 3개 + config). **그런데 포팅할 필요가 없다.**
`ml-explore/mlx-examples`의 `stable_diffusion/unet.py`가 SD의 UNet2DConditionModel을
MLX로 이미 구현해 두었고, 그 `load_unet`은 diffusers `config.json`에서 `UNetConfig`를
그대로 만든다 — `attention_head_dim`이 int면 `[값]*n_blocks`로 펼치는 것까지 포함해서.

MuseTalk v1.5 설정과 그 기본값의 차이는 **딱 셋**이다:

| 필드 | MuseTalk v1.5 | mlx-examples 기본값 |
|---|---|---|
| `in_channels` | **8** (마스크 잠재 + 참조 잠재) | 4 |
| `cross_attention_dim` | **384** (whisper 특징) | 1024 (CLIP) |
| `attention_head_dim` | **8** → heads (8,8,8,8) | num_heads (5,10,20,20) |

`block_out_channels`, `down_block_types`, `up_block_types`, `layers_per_block`,
`out_channels`, `norm_num_groups`, `act_fn`은 전부 동일하다. 검증:

```
torch state_dict 686 텐서 → mapped 718 배열
model params 718 | 매핑이 덮지 못한 것 0 | 갈 곳 없는 키 0
출력 코사인 0.999999 | 상대 L2 0.00113 | max|d| 0.01074
```

**타이밍 전에 수치를 먼저 봐야 한다.** 잘못 매핑된 UNet은 쓰레기를 빠르게 계산하고도
통과처럼 보인다.

### 배칭 ↔ 지연 트레이드오프는 실재한다 — 초판의 경고가 옳았다

PyTorch+MPS에서는 배치가 커질수록 프레임당 비용이 *나빠져서*, 한때 "지불할
트레이드오프가 없다"는 판단을 내렸다. **MLX에서는 반대이므로 그 판단은 철회한다.**

| N | UNet ms/배치 | 프레임당 | 정점 fps | 지연 | 처리량 | 지연 |
|---|---|---|---|---|---|---|
| 1 | 41.88 | 50.86ms | 19.7 | 130.9ms | 실패 | 통과 |
| **2** | **60.04** | **37.95ms** | **26.4** | **193.6ms** | **통과** | **통과** |
| 3 | 79.61 | 34.06ms | 29.4 | 257.6ms | 통과 | 7.6ms 초과 |
| 4 | 89.93 | 29.87ms | 33.5 | 312.6ms | 통과 | 실패 |
| 8 | 151.81 | 26.15ms | 38.2 | 553.1ms | 통과 | 실패 |

```
지연 = 80(룩어헤드) + (N-1)×41.67(배치 채우기) + UNet(N) + 디코드(N) + 3.97(합성)
```

`(N-1)×41.67`이 **배치 채우기 대기**다. 배치의 첫 프레임은 마지막 프레임의 오디오
윈도가 도착할 때까지 렌더될 수 없고 프레임은 41.67ms에 하나씩 온다. 그래서 배치를 그냥
살 수 없고, **가능한 창은 N=2 하나다.** N=3은 250ms를 7.6ms 넘긴다.

batch-1은 42.49ms로 PyTorch+MPS(44.47ms)와 사실상 같다 — **MLX의 이득은 전부 배칭에서
나온다.** 그래서 공개된 "~34 faces/sec (batch 8)"은 이상치가 아니라 진짜 batch-8
숫자였다.

**q4(int4 Linear 양자화)는 속도 레버가 아니지만 메모리 레버다.**
`nn.quantize(group_size=64, bits=4)`로 Linear만 양자화하면 속도는 **1.02~1.04배**로
사실상 변화가 없다 — SD UNet은 conv 중심이므로 당연한 결과다. 그런데 가중치가
**1.70 → 1.26GB(−26%)**로 줄고 품질은 우리 fp16 대비 코사인 **0.999553**으로
무손실급이다. N=2가 이미 30fps로 25% 여유를 갖고 있으므로, **남는 처리량 여유를
메모리와 바꾸는 거래로는 성립한다.** 상주가 문제가 되면 여기서 깎는다.

### 처리량 — 10분 연속은 이 제품에 없는 조건이었다

10분 연속 전력으로 재니 드리프트 **+41.2%**, 지속 20.11fps로 실패했다. **그 조건이
틀렸다.** MuseTalk은 `speaking` 중에만 돌고 `idle`·`listening`·`thinking`은 GPU가 0인
비디오 클립이다. 대화는 몇 초~수십 초 턴이고 사이에 회복 시간이 있다.

20초 발화 / 40초 유휴 ×10으로 다시 쟀다(N=2, MLX UNet + TAESD):

| 버스트 | 프레임당 p50 | p95 | fps | RSS |
|---|---|---|---|---|
| 1 | 33.17ms | 34.25 | 30.1 | 1.18GB |
| 5 | 33.65ms | 34.46 | 29.7 | 0.32GB |
| 10 | 33.00ms | 33.90 | 30.3 | 0.32GB |

**10/10 버스트가 24fps를 유지했다.** 드리프트 −0.5%로 사실상 0이고 p95도 34ms 안에
붙어 있어 튐이 없다.

**그리고 RSS가 1.18 → 0.32GB로 줄었다.** 유휴 구간마다 `mx.clear_cache()` +
`torch.mps.empty_cache()`를 부른 결과다. 이것이 앞선 +41.2%가 열이 아니라 **캐시
누적**이었다는 것을 확증한다 — 그 런은 캐시를 한 번도 비우지 않았다.

**유휴에 캐시를 비우는 것은 편법이 아니라 요구사항이다.** 말하지 않는 동안 GPU 버퍼를
들고 있을 이유가 없고, 비우지 않으면 드리프트가 돌아온다. 같은 원인으로 측정 중 개발
머신이 한 번 멈췄다(MLX와 PyTorch MPS를 한 프로세스에서 캐시 정리 없이 장시간 돌린
경우, 강제 리셋). **두 프레임워크를 한 프로세스에서 함께 돌리는 것은 측정을 오염시키고
머신을 위험하게 한다.**

### 정정 — 프레임 예산에서 whisper 인코더가 빠져 있었다

위 듀티 사이클 표의 33.17ms/프레임은 **UNet + TAESD만**이다. whisper 인코더 7.44ms가
빠져 있었고, 그것도 GPU에서 돈다. 넣으면:

| | ms/프레임 | fps | 여유 |
|---|---|---|---|
| 보고했던 값 (UNet + TAESD) | 33.17 | 30.1 | 25% |
| **실제 (whisper 포함)** | **40.61** | **24.6** | **2.5%** |

**여전히 통과하지만 1.06ms 차이는 측정 노이즈 안이다**(다른 항목에서 런 간 ±25%를 봤다).
편안한 통과가 아니라 선 위의 통과로 읽어야 한다.

**인코더를 K프레임당 1회로 분할하는 것은 기본값으로 삼을 수 없다.** 특징 차이를 재보니
K=5에서 평균이 「침묵 대 최대음량」 차이의 **77%**, 최대 143%였다 — 그 기준선은 눈에 보이는
입 변화(닫힘 → 이빨 보임)를 만든 크기다. K=2도 평균 37%다. 단 이 측정은 청크를 통째로
재사용해 **상한**을 잰 것이고, 실제 분할은 같은 인코더 출력에서 다른 인덱스를 슬라이스하므로
낡는 것은 최신 인덱스뿐이다. 실제 손해는 더 작지만 **재지 않았다.**

**윈도를 줄이는 길은 막혀 있다.** HF `WhisperEncoder`가 mel 3000프레임(30초)을 하드
체크하므로 7.4ms는 구현 차원에서 고정이다. 위치 임베딩을 잘라낸 커스텀 인코더로는 가능하나
학습 문맥을 바꾸는 변형이고 검증되지 않았다.

**되찾을 여유:** TAESD를 MLX로 옮기면 프레임워크 왕복(GPU→CPU 전송)이 사라진다 — 현재
숫자가 비용의 상한인 이유이고, 여유가 2.5%뿐인 지금은 그것이 최적화가 아니라 사실상
필요한 작업이 되었다.

### 전송과 로딩 — 측정된 두 가지 이득

**크롭박스만 보낸다.** 아바타 클립은 이미 브라우저에 있으므로 프레임 전체를 보낼 이유가
없다. 590×590 크롭박스만 JPEG q85로 보내면:

| | 인코드 | 크기 | 24fps 대역폭 |
|---|---|---|---|
| 전체 프레임 1080×1620 | 2.43ms | 174KB | 34.2 Mbit/s |
| **크롭박스만 590×590** | **0.46ms** | **52KB** | **10.1 Mbit/s** |

CPU 측이므로 GPU 듀티에는 영향이 없고, 전송량이 3.4배 줄어든다. (전체 프레임 값은 앞서
6.43ms로도 측정됐다 — 그때는 120회 루프에서 프레임이 매번 바뀌었고 여기서는 같은 프레임
반복이라 캐시가 따뜻하다. 진실은 둘 사이다.)

**MLX는 safetensors를 mmap한다.** 사전 변환된 파일을 쓰면 상주가 수요 기반이다:

| | RSS | 시간 |
|---|---|---|
| `mx.load` (1.70GB, 686 텐서) | 0.03GB | **3ms** |
| `mx.eval` 전체 실체화 | 1.62GB | 693ms |
| `del` + `mx.clear_cache()` | 0.03GB | — |

두 가지가 따라온다. **시작 비용이 없다** — 제품은 3.2GB torch 가중치를 변환하지 않고
사전 변환 MLX 파일을 3ms에 붙인다(스파이크의 2분짜리 변환은 측정 편의였다). 그리고
**긴 유휴에는 가중치를 놓을 수 있다** — 1.6GB를 일회성 693ms 예열과 바꾸는 선택지이며,
발화 턴 시작에 얹기엔 693ms가 크므로 "몇 분간 말이 없을 때"에만 쓸 수 있다.

*RSS를 믿지 말 것:* 이 실험은 raw safetensors를 직접 실체화했으므로 RSS에 잡혔지만,
모델 객체가 파라미터를 든 듀티 사이클 런에서는 활발히 계산하는 중에도 RSS가 0.32GB로
읽혔다. Metal 버퍼가 RSS에 온전히 잡히지 않는다. **계획은 가중치 바이트(1.70GB, q4로
1.26GB)로 세운다.**

### 기각된 대안 — 같은 아바타, 같은 음성으로 측정

| 모델 | 입 선명도 | ms/프레임 | 지연 | 기각 이유 |
|---|---|---|---|---|
| Wav2Lip 96² | 32~33% | 6.52 | 210ms | 화질 |
| Wav2Lip 256² (재학습 ONNX fp16) | 미측정 | 57~60 | 262ms | 처리량·지연 둘 다 |
| LivePortrait | — | ~250 (제3자, 같은 M4 Max) | — | 예산의 6배 |
| GeneFace++ / ER-NeRF | — | — | — | 학습 데이터 없음 |
| LatentSync | — | — | — | distillation 전제 |
| Wav2Lip-HD | — | — | — | 예산·깜빡임 |

**Wav2Lip 96²**는 연산에서 5배 이긴다(프레임당 6.52ms, 73MB, 24fps에 GPU 듀티 15.6%
대 MuseTalk 78%). 그런데 입 선명도가 원본의 32~33%로 **MuseTalk의 2.6배 흐리다.**
96×96은 입이 아니라 **얼굴 전체**이고 우리 얼굴은 화면에서 ~237px이므로 2.5배 확대다 —
§4.1의 "관대한 조건"은 사실이지만 96px 생성을 237px로 띄우는 경우까지 관대하지는 않다.
페이스트 방식 탓이 아니다: Wav2Lip 공식 `inference.py`가 얼굴 전체 박스를 되붙이는 것을
MuseTalk처럼 아래절반만 붙이도록 고치자 위쪽 얼굴 선명도는 24.6 → 85.8로 복구됐지만
**입은 25.4에서 움직이지 않았다.**

**Wav2Lip 계열의 룩어헤드는 200ms다** — 소스에서 확인(`hop_size=200`@16kHz = mel
프레임당 12.5ms, `mel_step_size=16`, 윈도가 프레임 자기 위치에서 시작). 학습 코드는
`crop_audio_window(spec, i-2)`로 1프레임 앞에서 시작해 160ms이고, `inference.py`는
오프셋이 없어 200ms다(공식 저장소 내부 불일치). 어느 쪽이든 MuseTalk의 80ms보다 크고,
그래서 예산에 46~90ms만 남는다. **256² 버전이 처리량과 지연 둘 다 넘긴 이유가 이것이다.**

**LivePortrait**의 논문 수치 ~12.8ms/프레임은 RTX 4090 + TensorRT 기준이다. 같은
M4 Max에서 제3자가 ONNX+CoreML로 보고한 값은 **4fps**(`warping_spade` fp16
180~250ms/프레임). 같은 저장소가 MuseTalk을 11~12fps로 보고해 우리 10.1fps를
확증하므로 이 대조군은 신뢰할 만하다.

**GeneFace++ / ER-NeRF**는 "입 주변 인페인팅 경계선이 구조적으로 없음"을 판다. 그런데
**우리는 그 문제가 없다** — 1:1 픽셀로 확인했고 가우시안 블러된 BiSeNet 마스크가 이음매
없이 섞인다. 반대로 우리에게 없는 것을 요구한다: NeRF 피팅에는 보통 실제 영상 3~5분이
필요한데 우리는 Kling으로 생성한 클립 ~70초뿐이고, 생성물이라 클립 간 3D 기하가
일관되지 않는다. 게다가 머리 전체를 렌더하므로 §4의 아바타 외형 자체가 바뀐다.

**LatentSync**는 1~2스텝 distillation이 전제이므로 스파이크가 아니라 연구 과제다.
그리고 base가 256² + SD VAE라 MuseTalk과 같은 디코드 비용을 물려받는다 — TAESD로
풀리지만 그러면 MuseTalk과 같은 자리다.

**Wav2Lip-HD**는 생성기를 재학습하지 않고 96² 출력을 Real-ESRGAN + GFPGAN으로
후처리한다. 재지 않고 예산으로 기각한다: 룩어헤드가 남긴 예산이 39ms인데 GFPGAN은
M시리즈에서 통상 그보다 크고(측정이 아니라 예산 추론이다), 얼굴 향상기는 프레임마다
독립적으로 디테일을 **환각**하므로 영상에서 깜빡인다 — TAESD에 프레임간 RMSE를 잰
이유가 정확히 그것이다. 그리고 얼굴 전체를 건드려 손대지 않은 부분의 정체성이 흔들린다.

### 계약 문제 — CONTRACTS 9, 구현보다 먼저 열어야 한다

**CONTRACTS 9는 단일 프로세스다.** MuseTalk 렌더 경로는 GB 단위 가중치를 든 상주 추론
루프이고 그 문장에 조용히 들어맞지 않는다. 1단계가 보태는 것은 충돌의 실제 형태다:

- **상주 메모리**: 가중치 기준 **약 1.75GB** — UNet fp16 1.70GB(측정) + TAESD 9MB +
  whisper-tiny fp16 ~16MB + 참조 잠재 6MB. **q4를 쓰면 약 1.3GB.**
  *RSS로 읽지 말 것*: PyTorch+SD-VAE 구성의 `ru_maxrss`는 3.88GB였으나 그것은 최고
  수위이자 다른 구성이고, MLX+TAESD 구성의 `ps` RSS는 정상 상태 0.32GB였으나 MLX의
  Metal 버퍼가 RSS에 온전히 잡히지 않아 과소 계상이다. 둘 다 깨끗한 답이 아니므로
  가중치 합을 쓴다.
- **발화 중 GPU 듀티 78%** (N=2, 프레임당 32.72ms 대 41.67ms). 유휴에는 0.
- 음성 경로와 경합하고, 그 경로는 **비협상 2번**(음성 지연 경로에 모델 호출 금지)이
  지배한다.

읽는 방법이 셋 있고 이 스파이크는 고르지 않는다 — 루프를 단일 프로세스 안에 두고
프로세스 내 GPU 워커를 허용하도록 개정 / 별도 프로세스를 정확히 하나 허용하도록 개정 /
립싱크를 별도 창에서만 돌리고 계약을 쓰인 대로 유지. **측정이 아니라 주인의 결정이다.**

### 설계는 깨지지 않는다

**MuseTalk은 `speaking` 렌더 경로만 대체한다.** activity 상태, mood 원샷, SSE,
크로스페이드, `_playback_until` 전부 그대로이고 나머지 10개 클립도 그대로 쓴다. 스위치
하나로 갈라지는 Phase 2로 두면 되고, **v1의 12개 클립은 어느 쪽이든 필요하다.**

한 가지 덧붙는다. 측정에 구동 클립으로 `idle2`를 썼다. MuseTalk은 아래쪽 얼굴을
마스크하고 다시 생성하므로 **구동 클립 자신의 입은 버려진다** — 즉 립싱크 경로에서
`speaking_soft`와 `speaking_loud`는 기여하는 것이 없고, 가장 살아 있는 idle 클립을
구동원으로 쓰게 된다. 비-립싱크 폴백으로는 그대로 필요하다.

### 스파이크 조건 (단계별, 죽일 조건을 맨 앞에)

| 단계 | 하는 일 | 비용 | 기각 조건 | 상태 |
|---|---|---|---|---|
| **0** | 공식 구현에서 오디오 윈도 구조를 읽는다 | 설치 0 | 미래 오디오 250ms 초과 | ✅ **통과 — 80ms** (v1.5 경로) |
| **1** | 공식 PyTorch + MPS로 오프라인 실행, 화질과 1080×1620 붙여넣기 포함 batch-1 지연 | ~8GB, 별도 venv | 화질 부족, 또는 합계 250ms 초과 | ✅ **통과 — 선명도 87%, 붙여넣기 2.42ms** |
| **2** | MLX 포팅으로 처리량 확보 | 며칠 → **시간** | 24fps 미달 | ✅ **통과 — N=2에서 30fps, 지연 191ms** |
| **3** | 스위치 게이트 구현 | — | — | CONTRACTS 9 논의 후 |

**2단계가 "며칠"에서 "시간"으로 준 이유**는 `mlx-examples`의 UNet이 config 기반이라
파이프라인을 포팅할 필요가 없었기 때문이다. 반대로 **1단계가 예상보다 컸다** — TAESD
교체와 듀티 사이클 발견이 거기서 나왔다.

  쓸 수 없었다(Command Line Tools에 C++ 표준 헤더가 없어 inductor CPU 백엔드가 빌드되지
  않는다). 커널 퓨전이 없는 상태의 숫자다.
- **입력**: `data/face/idle2.mp4`(1080×1620, 24fps, 193프레임) + 한국어 25.4초,
  `say -v Yuna`, 24kHz 모노 s16 — 실제 Gemini Live 재생 포맷
- **타이밍**: GPU 구간마다 `torch.mps.synchronize()` / `mx.eval()`. 워밍업 폐기,
  구성당 30~40 샘플, p50 보고
- **대체한 것**: 68점 랜드마크를 DWPose/mmpose가 아니라 face_alignment FAN(2DFAN4)에서
  얻었다(mmcv에 macOS arm64 휠이 없다). 둘 다 iBUG-68 체계라 박스 공식을 그대로 썼고,
  결과 박스는 신뢰하지 않고 눈으로 확인했다. 준비 단계 전용이며 지연 경로 밖이다.
- **런 간 편차**: fp32 batch-1이 한 런 97.8ms, 다른 런 126.0ms(±25%). 더 좋은 쪽만
  쓰지 않았다.
- **재지 않은 것**: 전부 MLX인 구현(현 측정은 TAESD가 PyTorch/MPS라 한 프로세스가 두
  프레임워크로 GPU를 민다 — **비용의 상한이지 하한이 아니다**). 실제 Gemini Live 소켓이
  파이프라인을 먹이는 경우. 브라우저 쪽 JPEG 디코드와 페인트. `idle2` 외의 클립.
  whisper 인코더를 프레임 간 분할하면 화질이 깎이는지. Wav2Lip 256²의 화질.

**스파이크 코드는 저장소에 남기지 않는다.** 실제 키나 GB급 가중치가 필요한 검사이므로
`tests/`에 들 수 없고, 한 번의 판정을 위한 것이므로 `evals/`에 두어도 다시 돌 일이 없다.
재현이 필요하면 이 절의 숫자와 조건으로 다시 만든다.

### 남은 것

1. **CONTRACTS 9 논의** — 구현보다 먼저. 위 세 읽기 중 하나를 고르는 일.
2. **TAESD를 MLX로 포팅** — 게이트가 아니라 최적화다. 두 프레임워크를 한 프로세스에서
   돌리는 것을 없애면 숫자가 나아지고 측정도 깨끗해진다.
3. **유휴 구간의 캐시 정리를 설계에 넣는다** — 빠지면 드리프트가 돌아온다.
4. **선명도 87%가 실물에서 충분한지는 주인이 본다.** §「테스트」가 말한 대로 이 기능은
   "느낌"이 요구사항이고 자동 검증이 구조적으로 닿지 않는다. 숫자는 통과선을 넘었을 뿐이다.

## 테스트

- **단위** — 버스: 구독자 0명이면 no-op, level 덮어쓰기(큐 아님), 스냅샷 우선 발행.
  태그 스트리퍼: 태그가 전송 텍스트와 마크다운 양쪽에서 제거되는지, 태그 없을 때
  이벤트가 안 나가는지, 태그처럼 생긴 주인 입력이 mood를 만들지 않는지.
  `speaking`이 `_playback_until` 경계에서 정확히 켜지고 꺼지는지(가짜 시계로).
  RMS 엔벨로프의 어택/릴리즈 비대칭. flourish 타이머가 activity 변화에 잘리는지.
- **reachability** (`tests/test_reachable.py`) — `/face`와 `/face/stream`에 호출자가
  있는지, `FaceState`/`OneShot`을 무언가가 구성하는지.
- **acceptance** (`tests/test_acceptance.py`) — 대화 한 턴을 실제로 굴려서 SSE에
  `thinking → speaking → idle`이 순서대로 나오는지, mood 태그가 이벤트가 되고
  마크다운에는 없는지.
- **직접 돌려본다** — pytest는 동작의 증명이 아니다. 얼굴 창을 열고 음성 대화를
  한 번 하고, 검은 프레임·입 지연·전환 이음매를 눈으로 본다. 이 기능은 "느낌"이
  요구사항이라 자동 검증이 구조적으로 닿지 않는다.

### 에셋 QA — 부위별로 재라

**전체 프레임 평균은 거짓 음성을 낸다.** `speaking` 두 클립은 전체 프레임 움직임
지표로는 꼬리 0.25~0.88초만 얼었다고 나왔고, **입 영역만 재니 2.12초였다** — 입이
멈춘 동안 몸은 계속 움직이니 평균에 묻혔다. 관심 있는 부위를 따로 잘라 재야 한다.

| 재는 것 | 방법 | 통과선 (현재 에셋 실측) |
|---|---|---|
| 루프 이음매 | 첫↔끝 프레임 RMSE | 1.09 ~ 1.22 |
| 그레인 기어다님 | **진짜 배경**(좌상단 등)의 프레임간 RMSE | 0.08 ~ 0.21 |
| 카메라 밀림 | 배경 t=0 대비 시계열 RMSE | 0.48 ~ 0.82 |
| 얼어붙은 구간 | 관심 부위의 프레임간 RMSE가 중위값의 35% 미만인 연속 구간 | 트림 후 0 |
| 클립간 일관성 | 해상도·fps·배경색이 전부 같은가 | 1176×1764 · 24 · `#19191B` |

**주의 둘.** 배경 영역을 잡을 때 인물의 팔·머리가 들어가면 카메라 드리프트가
7~10으로 잡혀 "카메라가 움직인다"는 오판이 나온다 — 좌상단 코너처럼 확실한 배경만
쓴다. 그리고 **깜빡임 검출은 클립별로 눈 박스를 맞춰야 한다** — 12개에 같은 박스를
쓰면 시선·머리 움직임을 깜빡임으로 잡는다(연속 프레임이 줄줄이 플래그되는 것이
증거다).
