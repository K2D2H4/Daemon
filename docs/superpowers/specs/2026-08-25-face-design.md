# 얼굴 — 데몬에게 외형을 주는 설계

- 작성 2026-08-25
- 상태: 계획 승인 대기 (approved for planning)
- 브랜치: `claude/daemon-appearance-animation-8393b7`

미리 렌더한 짧은 영상 클립 몇 개와, 그 클립을 **무엇이 고르는가**에 대한 설계다.
클립을 만드는 건 쉬운 쪽이고 어려운 쪽은 후자다. 이 파일의 목적은 그 후자를
못박는 것이며, 산문보다 결정이 중요하다.

근거 규칙: CONTRACTS 2(음성 지연 경로에 모델 호출 금지)·4(레이어링)·9(단일
프로세스)·12(툴 감사 행). 재사용: [admin 웹 설계](../../design/2026-08-07-m5-admin-web-design.md)의
"인증 없음 = 오리진을 증명할 수 없음 = 그런 경로를 만들지 않는다" 태도.

## 무엇이고 무엇이 아닌가

**이다.** 상시 떠 있는 앰비언트 존재감이자 음성 대화 중의 얼굴. 로컬호스트
페이지 하나(`/face`)를 앱 창으로 띄운다.

**아니다.** 립싱크가 아니다(음소 단위로 맞추지 않는다). 런타임 생성이 아니다.
아바타 커스터마이징 UI가 아니다. 네이티브 앱이 아니다.

## 승인된 결정

| # | 결정 | 버린 것 |
|---|---|---|
| 1 | 앰비언트 + 대화 얼굴 둘 다. **지연 최소화가 최우선** | 데모/쇼케이스 전용 |
| 2 | 표정 = 결정론적 activity + **모델이 선언하는 mood** | 결정론만 / 코드 휴리스틱 |
| 3 | 입은 **RMS 진폭 기반**. 오디오는 브라우저로 보내지 않는다 | 립싱크 없음 / 진짜 립싱크 |
| 4 | 같은 서버의 **전용 `/face` 라우트**, 앱 창으로 띄움 | admin 안의 탭 / 네이티브 창 |
| 5 | 에셋은 **주인 소유**, `~/.daemon/face/`. 리포에 동봉하지 않음 | 기본 얼굴 동봉 / 폴백 |
| 6 | **허브-앤-스포크**: 루프 4 + 원샷 3, 모두 같은 중립 포즈에서 시작·종료 | 상태당 루프만 / N² 전이 클립 |

**런타임 생성은 불가능하다.** 생성 모델은 클립 하나에 수십 초~수 분이 걸린다.
클립은 전부 미리 렌더하고 브라우저가 preload한다. 따라서 지연 예산은 (1) 상태
신호가 브라우저에 닿는 시간, (2) 클립이 바뀌는 시간뿐이다.

## 비목표 (v1, YAGNI)

- 음소 단위 립싱크
- 음성 경로의 `sulky` / `curious` (§5 참조)
- 아바타 교체 UI — 파일을 디렉토리에 넣는 것이 인터페이스다
- 여러 아바타 프로필
- 원격/비-로컬호스트 접근

## 1. 상태 모델

**축이 두 개고 성격이 다르다.**

| | 무엇 | 성격 | 클립 |
|---|---|---|---|
| `activity` | `idle / listening / thinking / speaking / working` | 지속 **상태** | 루프 |
| `mood` | `amused / sulky / curious` | 일회성 **이벤트** | 원샷 |

mood를 상태가 아니라 이벤트로 두는 것이 핵심이다. 기분에 시작·끝 시각을 붙이는
순간 "언제 풀리는가"라는 답 없는 질문이 생기고(타이머? 다음 턴? 화제 전환?)
전부 추측이 된다. 웃음은 상태가 아니라 일어나는 일이다. 그리고 이 데이터
모델이 결정 6의 애니메이션 모델과 같은 모양이다 — 루프 ← activity, 원샷 ← mood.

### 새 모듈 `daemon/face.py`

```python
Activity = Literal["idle", "listening", "thinking", "speaking", "working"]
Mood = Literal["amused", "sulky", "curious"]

@dataclass(frozen=True, slots=True)
class FaceState:
    activity: Activity
    level: float          # 0.0..1.0, speaking 중에만 의미 있음

@dataclass(frozen=True, slots=True)
class MoodEvent:
    mood: Mood
```

버스 하나가 이 둘을 나른다. **daemon 안의 어떤 구현도 import하지 않는다**
(CONTRACTS 4). 발행자는 버스를 주입받지 import하지 않으며, `daemon/app.py`가
조립한다.

**구독자가 0명이면 발행은 비교 한 번이다.** 얼굴 창을 안 열어두면 이 기능
전체가 공짜다. 텍스트 전용 설치는 아무 비용도 내지 않는다.

**level은 버퍼링하지 않고 덮어쓴다.** 구독자별 "최신값 슬롯" 하나만 둔다. 큐를
쓰면 느린 구독자 뒤로 입 모양이 밀려 쌓이는데, **밀린 입 모양은 건너뛴 입
모양보다 훨씬 나쁘다.**

### 신호의 출처

| 신호 | 출처 | 이미 아는가 |
|---|---|---|
| `listening` | `voice/conversation.py` — 마이크 열림 + VAD가 주인 발화 판정 | 예 |
| `thinking` | 요청 전송 후 첫 오디오/토큰 전까지 | 예 |
| `speaking` | 첫 오디오 청크 ~ 재생 큐가 350ms 이상 빔 | 예 |
| `working` | `tools/runner.py` — decide → execute 구간 | 예 |
| `idle` | 위 어느 것도 아님 | 예 |
| `level` | `voice/audio.py` `_drain`의 RMS | 계산만 |
| `mood` | 모델이 선언 | **유일하게 새로 만드는 것** |

activity 다섯 개는 코드가 이미 알고 있는 사실이다. 새로 추론하는 것이 없어서
지연도 0이고 틀릴 수도 없다.

### RMS는 `play()`가 아니라 `_drain`에서 잰다

**이 한 줄이 "살아있다"와 "섬뜩하다"를 가른다.**

`play()`는 큐에 넣는 것이다(`voice/audio.py:274`). 실제로 들리는 것은 `_drain`이
`stream.write` 할 때다(`:348`). `play()` 시점에 RMS를 재면 **큐 깊이만큼 소리보다
앞서간다** — 입이 먼저 움직이고 소리가 나중에 난다.

구현: `PortAudioIO.__init__`에 `on_level: Callable[[float], None] | None = None`
하나를 추가한다(`voice/audio.py:109`). 순수 추가이며, `audio.py`는 "얼굴"이라는
개념을 알 필요가 없다 — 자기가 내는 소리의 크기를 보고할 뿐이다.

### mood 태그는 기억에 닿지 않는다

텍스트 경로에서 모델이 응답 맨 앞에 태그를 붙이고, **함수 하나가 그것을
떼어낸다 — 전송 전에도, 마크다운에 쓰기 전에도.** 태그가 대화 로그에 남으면
recall이 그것을 다시 프롬프트에 실어나르고 결국 페르소나로 세탁된다. 태그가
없으면 mood 이벤트 없음(중립으로 되돌리지 않는다 — 되돌릴 상태가 없다).

## 2. 전송

**SSE 하나. `speaking` 중에만 흐른다.**

```
GET /face/stream    text/event-stream
```

세 종류가 한 스트림에 실린다 — activity 변화, mood 이벤트, level 틱. 앞의 둘은
일어날 때만, level은 말하는 동안에만 25Hz. 조용할 때는 소켓이 열려만 있고
트래픽이 0이다.

**WebSocket이 아닌 이유.** 브라우저→데몬 방향이 없어 단방향으로 충분하고,
결정적으로 **재접속이 브라우저에 내장**돼 있다. `daemon update`나 재시작 뒤에
얼굴 창이 알아서 다시 붙는다. WS면 그 로직을 직접 짜야 하고, 그 실패는 항상
"얼굴이 굳은 채로 남는" 쪽이다. 루프백에서 지연 차이는 없다(25msg/s × 40B ≈ 1KB/s).

**첫 이벤트는 변화가 아니라 스냅샷이다.** 없으면 재접속 직후 데몬이 말하는
중인데 얼굴은 idle에 앉아 있다.

**level은 전송 계층에서도 합친다.** 창이 가려져 소비가 느려질 때 밀린 값이
쌓이면, 창을 다시 봤을 때 입이 소리보다 몇 초 뒤처진 채 따라온다. 큐 없음.

**읽기 전용이고 부수효과가 없다.** admin이 오리진 게이트 때문에 툴 경로를 아예
만들지 않은 것과 같은 이유로, 여기도 "지금 무엇을 하는 중인가" 외에는 아무것도
나가지 않고 아무것도 들어오지 않는다. 대화 내용은 나가지 않는다 — activity
이름과 float 하나가 전부다.

**지연 예산:** 프로세스 안 발행 → 루프백 SSE 쓰기 = 이벤트 루프 한 틱, 1ms
미만. 실제로 느껴질 지연은 전송이 아니라 크로스페이드이고, 그것은 줄여야 할
지연이 아니라 일부러 넣는 것이다.

## 3. 페이지와 재생

자연스러움이 여기서 결정된다.

### 3.1 클립은 미리 로드하고 디코더까지 예열한다

7개 전부 `<video muted loop playsinline preload="auto">`로 겹쳐 쌓고 하나만
`opacity: 1`. 로드 직후 각각 한 번 `play()` 후 즉시 `pause()`로 **첫 프레임을
디코드시켜 둔다.**

이걸 빼면 처음 전환되는 클립에서 검은 프레임이 한 번 번쩍한다. 지연 예산을
아무리 줄여도 이것 하나면 무너진다. 예열은 페이지 열 때 한 번, 이후 비용 0.

**메모리 비용(붙들고 있는 디코드 프레임 7장):**

| 소스 (2:3) | 프레임 1장 | 7장 상주 |
|---|---|---|
| 1080×1620 | 7.0MB | **49MB** |
| 1440×2160 | 12.4MB | 87MB |
| 3840×5760 | 88.5MB | **619MB** ← 벽 |

(`working.mp4`까지 만들면 8장 기준으로 읽는다.) 연산이 아니라 메모리가 벽이다. 7개 중 6개는 일시정지 상태로 프레임 한 장만
붙들고 있고, 재생 중인 것은 1개(크로스페이드 중에만 2개)다.

### 3.2 전환은 180ms 크로스페이드 — 단 idle 복귀는 루프 끝을 기다린다

컷(0ms)은 포즈가 같아도 조명·미세움직임 차이로 튄다. 400ms를 넘기면 두 얼굴이
겹친 것이 인지된다(고스팅). **180ms**가 안전한 지점이다.

**idle로 돌아갈 때만 아웃고잉 클립이 루프 끝(=중립 포즈)에 닿을 때까지 최대
500ms 기다린다.** 나머지 전환은 이미 사건이 일어났으니 즉시 가야 하지만, idle
복귀는 지금이어야 할 이유가 없는 유일한 전환이고 동시에 가장 자주 일어나는
전환이다. 여기서만 기다리면 가장 흔한 전환이 거의 보이지 않게 된다.

전환 시 들어오는 클립은 `currentTime = 0`으로 되감고 `play()` 한다. 이미
디코드돼 있으므로 한 프레임 안에 시작한다(§4의 짧은 GOP가 이것을 보장한다).

### 3.3 입: `playbackRate`를 엔벨로프로 변조 (0.85 ~ 1.25)

RMS 원본은 너무 떨려 그대로 쓰면 입이 경련한다. **빠른 어택(~30ms) / 느린
릴리즈(~150ms)** 비대칭 엔벨로프를 씌운다 — 실제 입이 그렇게 움직인다. 빨리
열리고 천천히 닫힌다.

범위를 조이는 이유: 0.8 아래는 슬로모션, 1.3 위는 배속으로 보인다. 둘 다
정확히 섬뜩함이 사는 곳이다.

**문장 중간 쉼(100~300ms)은 따로 처리하지 않는다.** 릴리즈가 알아서 느려지게
만들고 그것이 맞다 — 쉼표 하나에 입을 완전히 닫는 사람은 없다.

### 3.4 `speaking` 종료는 큐 빔 + 350ms 디바운스

재생 큐가 비는 것을 종료 신호로 쓰는데, 모델이 오디오를 버스트로 보내면 발화
중간에도 큐가 순간 빈다. 디바운스 없이 쓰면 한 문장 안에서 얼굴이 idle과
speaking을 오간다.

### 3.5 mood 원샷은 도착 즉시 재생하고, `speaking`이 자른다

텍스트 경로에서 태그는 응답과 함께 오므로 **말이 시작되기 직전**에 도착한다.
그때 바로 재생하면 표정이 먼저 뜨고 말이 시작된다 — 사람이 하는 순서다.

말을 늦추지는 않는다. 오디오가 시작되면 원샷은 그 자리에서 speaking으로
크로스페이드되며 잘린다. thinking→speaking 간격이 보통 1초쯤이라 대개 다
재생되고, 안 되면 잘린 채로도 자연스럽다.

### 3.6 에셋이 없거나 일부만 있어도 동작한다

`~/.daemon/face/`가 비면 `/face`는 404가 아니라 **제작 안내(§4)**를 띄운다.
`idle.mp4` 하나만 있어도 돌아간다. 폴백 사슬은 하나뿐이다 —
`working → thinking → idle`, `listening → idle`, `speaking → idle`, 그리고 mood
원샷은 없으면 **아무 일도 일어나지 않는다**(idle로 대체하지 않는다. 웃으라는
신호에 무표정한 루프를 트는 것은 표정이 없는 것보다 나쁘다). 주인이 7개를
한 번에 다 만들 필요가 없어야 한다.

### 3.7 곁다리

애니메이션 시간 계산을 `requestAnimationFrame`으로 하지 않는다. `<video loop>`
재생은 네이티브라 백그라운드 스로틀과 무관하지만 rAF는 스로틀된다. rAF는
`playbackRate` 갱신에만 쓴다 — 스로틀되면 덜 자주 갱신될 뿐 어긋나지 않는다.

페이지는 admin처럼 자족형 HTML 한 장, 크롬 없는 단색 배경.
`daemon face`가 `--app=http://127.0.0.1:PORT/face`로 연다.

## 4. 에셋 사양 — 주인이 실제로 뽑을 것

### 4.1 프레이밍

**명치 바로 아래까지, 손은 프레임 밖. 2:3 세로, 1080×1620.**

상반신인 이유: 어깨와 상체의 미세한 움직임이 "살아있음"의 대부분을 만든다.
떠 있는 머리보다 낫고, `listening`의 기울임이나 `sulky`의 어깨 돌리기는 표정보다
잘 읽힌다.

**손을 빼는 이유:** 생성 모델이 가장 자주 망치는 것이 손이고, 종일 켜두는
창에서 손가락이 여섯 개가 되는 순간이 있으면 그 순간이 그 창의 전부가 된다.
넣고 싶다면 재시도 예산을 2배로 잡는다.

**2:3인 이유:** 명치 아래까지 담으려면 4:5(1350)로는 세로가 부족하고 3:4(1440)도
모자란다. 같은 폭에서 세로만 늘려야 **얼굴 폭을 유지한 채** 몸통이 더 들어온다.
9:16(1920)은 허리 아래까지 담겨 폰 모양이 되고 데스크톱 구석 창으로 과하다.
모델이 2:3을 주지 않으면 9:16으로 뽑아 §4.5에서 크롭한다.

**받아들인 대가 — 얼굴이 작아진다.** 프레임에 몸이 더 들어오면 얼굴 비율이 준다.

| 프레이밍 | 소스에서 얼굴 폭 | 400pt 창(=800px)에 띄웠을 때 |
|---|---|---|
| 가슴 위 | ~400px | ~296px |
| 명치 아래 (채택) | ~280px | **~207px** |

**해상도로는 메울 수 없다.** 소스를 1440폭으로 올려도 창 크기가 같으면 표시 픽셀은
같다. 얼굴을 키우는 유일한 방법은 창을 키우는 것이고, 그것은 돈이 아니라 모니터
자리를 내는 일이다. 207px면 깜빡임·입 움직임·고개 갸웃은 충분히 읽히고, 잃는 것은
피부 질감이다. 주인이 알고 선택했다.

**손을 빼는 것이 여기서 더 중요해진다.** 명치 아래까지 내려가면 팔이 많이 들어오고
손이 프레임 하단 경계에 걸린다. **잘린 손은 온전한 손보다 나쁘다** — 모델이 반쯤
잘린 손을 만들어놓고 프레임마다 뒤튼다. 하단을 명치 바로 아래에서 끊으면 팔은
보이되 손은 아래로 빠진다.

### 4.2 클립 7개 (+ 선택 1)

| 파일 | 종류 | 길이 | 내용 |
|---|---|---|---|
| `idle.mp4` | 루프 | **8~10초** | 호흡, 가끔 눈 깜빡임, 아주 미세한 무게중심 이동. 아무 일도 일어나면 안 됨 |
| `listening.mp4` | 루프 | 6~8초 | 살짝 앞으로 기울임, 시선 고정, 깜빡임 줄어듦 |
| `thinking.mp4` | 루프 | 6~8초 | 시선을 위/옆으로, 눈썹 약간, 입 다뭄 |
| `speaking.mp4` | 루프 | 4~6초 | 입 움직임 + 자연스러운 머리 미동. 내용과 무관한 중립 발화 |
| `working.mp4` | 루프 | 6~8초 | **선택.** 만들지 않으면 §3.6의 폴백 사슬을 탄다 |
| `amused.mp4` | 원샷 | 1.5~2.5초 | 웃음 |
| `sulky.mp4` | 원샷 | 1.5~2.5초 | 삐침 |
| `curious.mp4` | 원샷 | 1.5~2.5초 | 고개 갸웃 |

필수는 7개이고 `working.mp4`만 선택이다. 만들면 §3.1의 상주 프레임이 8장이 된다.

**`idle`에 재시도 예산을 가장 많이 쓴다.** 압도적으로 오래 보이는 클립이고,
짧을수록 루프가 티난다. 8초 루프는 알아채기 어렵지만 3초 루프는 30초만 봐도
패턴이 보인다. 반대로 `speaking`은 짧아도 된다 — 입이 계속 움직이는 동안엔 루프
경계가 보이지 않고, `playbackRate` 변조가 주기 자체를 깬다.

### 4.3 제작의 핵심 제약

> **모든 클립은 같은 중립 포즈에서 시작해서 같은 중립 포즈로 끝난다.**

이 한 줄이 N² 전이 클립을 불필요하게 만든다.

1. **기준 이미지 한 장을 먼저 확정한다.** 이 한 장이 "중립 포즈"의 정의다.
2. **7개 전부 그 한 장에서 image-to-video로 뽑는다.** 클립마다 이미지를 새로
   만들면 미묘하게 다른 사람이 된다 — 가장 흔한 실패이며, 크로스페이드에서
   얼굴이 흐물거리는 것으로 드러난다.
3. 프롬프트 끝에 항상 `returns to the exact starting pose and expression at the end`.
4. 그래도 완벽히는 맞지 않는다. 마지막 손질은 생성이 아니라 편집으로 한다(§4.5).

### 4.4 프롬프트 템플릿

기준 이미지(한 번만):

```
Upper body portrait of a woman in her mid-to-late twenties.
Long light blonde hair, bright blue eyes, fair skin.
Wearing a fitted sleeveless turtleneck in deep muted forest green.
Curvy figure. Confident, aloof, composed. Slightly haughty.
Framed from just below the solar plexus up. Arms visible, hands out of frame.
Completely neutral, relaxed resting expression. Mouth closed. Not smiling.
Looking straight at the camera.
Plain flat solid #1C1C1E background, no texture, no gradient, no props.
Even soft frontal lighting, no hard shadows.
2:3 vertical composition, 1080x1620.
Photorealistic, sharp focus on the face, natural skin texture.
```

**의상 색이 `#1C1C1E`와 붙으면 안 된다.** 검정 상의는 명도가 배경과 같고 채도도 0이라
몸통이 배경에 먹혀 머리와 어깨만 뜬다 — 상반신을 보여주려는 목적과 정면으로 어긋난다.
깊은 녹색(`#2A4034`)이나 와인(`#5A2233`)은 배경이 무채색이라 **색상 대비로 분리된다.**
녹색을 채택한 이유는 둘이다: 금발·벽안과 차가운 톤이 맞고, **4:2:0 크로마 서브샘플링이
채도 높은 빨강 계열을 가장 심하게 뭉갠다**(§4.5가 `yuv420p`를 쓴다). 어느 쪽이든
`muted`를 넣는다 — 쨍한 원색은 니트 질감이 뭉개진다.

**`Not smiling`을 빼지 않는다.** 기준 이미지가 곧 중립 포즈의 정의이고 7개 클립이 전부
여기서 시작해 여기로 돌아온다. 웃는 기준 이미지를 잡으면 `sulky`가 웃다가 삐치고 다시
웃는 것으로 끝난다. 생성 모델은 예쁜 것을 주려는 편향이 강해 명시적으로 막아야 한다.
다행히 **도도한 인상은 중립 포즈로 이상적이다** — 표정을 짓지 않으면서 표정이 있는
상태라, 무표정 기준 이미지가 밋밋해지는 문제가 사라지고 `amused`와의 대비도 커진다.

생성은 **Higgsfield Soul 2.0**을 먼저 쓴다(영상과 같은 플랫폼이라 이미지가 곧바로
image-to-video 입력이 되고, 구독을 하나만 낸다). 실사 특화 모델은 지시를 "예쁘게"
해석하는 편향이 있어 계속 미소가 나오면, 지시 준수가 강한 범용 모델(Gemini/GPT 계열)로
구도·표정을 잡고 그 결과를 **Soul Image-to-Image**에 넣어 텍스처만 올린다. Soul ID는
20장 이상의 학습 이미지를 요구해 존재하지 않는 인물에겐 순환이고, §4.3이 "1장을 7번
재사용"으로 정체성 문제를 이미 구조적으로 푸므로 **쓰지 않는다.**

모든 클립에 공통으로 붙이는 꼬리(고정):

```
static camera, no pan, no zoom, no camera movement.
same lighting, same background, same clothing, same framing.
hands stay out of frame, no gestures.
returns to the exact starting pose and expression at the end.
```

- **정적 카메라**를 명시하지 않으면 크로스페이드 시점마다 구도가 어긋난다.
- **단색 배경**이어야 한다. 복잡하면 클립마다 배경이 미묘하게 달라지고
  크로스페이드에서 배경이 출렁인다. 페이지 배경색과 맞추면 창 경계도 사라진다.
- **`hands stay out of frame, no gestures`가 정지 이미지의 프레이밍만으로는
  부족하다.** 명치 아래 프레이밍은 팔을 보여주므로, 영상 모델이 말하는 동작에
  어울리는 제스처를 만들려고 손을 프레임 안으로 올린다. 기준 이미지에 손이 없어도
  일어난다 — 움직임을 새로 만드는 단계이기 때문이다.

클립별 본문 (확정):

| 클립 | 프롬프트 본문 |
|---|---|
| `idle` | `breathing calmly, occasional natural blink, very subtle weight shift. nothing happens.` |
| `listening` | `leaning slightly forward, attentive, steady eye contact, fewer blinks.` |
| `thinking` | `eyes drifting up and to the side, slight brow movement, lips closed.` |
| `speaking` | `talking naturally, mouth moving, small natural head motion.` |
| `amused` | `bursting into a warm laugh, then settling back.` |
| `sulky` | `pouting, turning the shoulder away slightly, then settling back.` |
| `curious` | `tilting the head, raising an eyebrow, then settling back.` |

### 4.5 인코딩

**H.264 MP4, 30fps, 키프레임 간격 0.5초(`-g 15`), 오디오 없음.**

VP9/WebM이 아닌 이유: 디코더 7개를 항상 물고 있으므로 하드웨어 디코드가 확실한
코덱이어야 한다. H.264는 macOS의 모든 브라우저에서 하드웨어 디코드된다. 배경을
페이지 색과 맞추면 알파 채널도 필요 없다.

짧은 GOP가 중요한 이유: 전환할 때 `currentTime = 0`으로 되감는데, 키프레임이
드물면 되감기가 한 박자 늦는다. 파일이 조금 커지지만 로컬 파일이라 무관하고,
되감기 지연은 바로 보인다.

**9:16으로 뽑았다면 2:3으로 크롭(상단 정렬 — 머리를 지키기 위해):**

```bash
ffmpeg -i raw.mp4 -vf "crop=iw:iw*3/2:0:0" -an cropped.mp4
```

**루프 클립 — 끝 0.3초를 앞 0.3초에 크로스디졸브해 seamless loop로 만든다:**

```bash
IN=cropped.mp4; OUT=idle.mp4; X=0.3
D=$(ffprobe -v error -show_entries format=duration -of csv=p=0 "$IN")
OFF=$(python3 -c "print(max(0.0, $D - 2*$X))")
ffmpeg -i "$IN" -filter_complex \
"[0:v]trim=start=$X,setpts=PTS-STARTPTS[body];\
 [0:v]trim=start=0:end=$X,setpts=PTS-STARTPTS[head];\
 [body][head]xfade=transition=fade:duration=$X:offset=$OFF[v]" \
 -map "[v]" -an -c:v libx264 -pix_fmt yuv420p -r 30 -g 15 -crf 18 "$OUT"
```

결과물의 첫 프레임과 마지막 프레임이 모두 원본 `t=X` 시점의 프레임이 되어
루프가 이어진다. 길이는 `D - X`.

**원샷 클립 — 루프 처리 없이 재인코딩만:**

```bash
ffmpeg -i cropped.mp4 -an -c:v libx264 -pix_fmt yuv420p -r 30 -g 15 -crf 18 amused.mp4
```

원샷은 루프가 아니므로 이음매 처리를 하지 않는다. 대신 **시작·끝 프레임이
`idle`의 중립 포즈와 같아야** 크로스페이드가 보이지 않는다.

## 5. 음성 경로의 mood — v1에서는 넣지 않는다

### 문제

텍스트 경로는 쉽다 — 모델이 태그를 붙이고 우리가 뗀다. **음성엔 우리가 손댈
텍스트가 없다.** 오는 것은 오디오·트랜스크립트·툴 콜뿐이고, 트랜스크립트에 태그를
넣게 하면 그것을 소리 내어 읽는다.

### 툴로 받는 것이 답처럼 보이지만 CONTRACTS 12가 막는다

`set_mood(mood: string)`은 flat 스키마라 음성이 실제로 호출할 수 있다 —
`delegate_task`가 증명했듯 nested만 위조되고 flat은 된다
([async-delegation 설계](2026-08-14-async-delegation-design.md)).

그러나 CONTRACTS 12는 실행된 툴 콜이 전부 `tool_calls` 감사 행을 남기게 하고,
그 행의 목적을 "주인의, 무엇이 이 기계를 건드렸는지에 대한 ground-truth 기록"
이라고 명시한다. **기분이 바뀐 것은 기계를 아무것도 건드리지 않았다.** 매 턴 mood
행이 쌓이면 `run_command`·`write_file` 행이 그 밑에 묻힌다. 감사 로그가
노이즈로 희석되는 것은 감사 로그가 고장 나는 방식이다.

**이것은 계약이 막는 것이 아니라 "mood는 툴이 아니다"라고 알려주는 것이다.**
감사 행을 건너뛰는 예외를 만드는 것은 계약이 "필요하면 멈추고 알려라"라고 적어둔
바로 그 상황이며, 조용히 우회할 문제가 아니다.

### v1 결정

음성 중에는 **activity 4종 + level만** 흐른다. 정직하게: **음성 대화 중에는 웃음도
삐침도 나오지 않는다.** 표정이 `listening → thinking → speaking → idle`로만 움직인다.

손실이지만 실제로는 적다. 음성 대화의 대부분 시간은 저 4개 중 하나이고, 입이
소리 따라 움직이고 몸이 기울고 시선이 움직이는 것만으로 존재감의 대부분이 나온다.

### 첫 후속: 웃음은 오디오에서 검출할 수 있다

결정 2에서 "코드가 감정을 추측"하는 것을 버렸는데, 그것은 **텍스트에서 단어로
감정을 추론**하는 것이었고 측정에서 실패했다(`MEASURED.md`: 주인 발화 463개에
감정 렉시콘 매치 0개).

**데몬 자신이 낸 소리에서 웃음을 잡는 것은 다른 종류다.** 감정을 추론하는 것이
아니라 웃음이라는 사건이 실제로 일어난 것을 관측하는 것이다. 웃음소리는 4~7Hz의
주기적 에너지 버스트로 음향적 특징이 뚜렷하고, **우리는 이미 `_drain`에서 RMS를
계산한다.** 엔벨로프만 보면 된다. 새 툴 없음, 새 모델 호출 없음(CONTRACTS 2 유지),
감사 행 없음, 계약 변경 없음.

무엇보다 — **소리 내어 웃는데 얼굴이 가만히 있는 것은 얼굴이 아예 없는 것보다
나쁘다.** 그 순간이 환상이 깨지는 지점이다.

**데이터 없이 임계값을 튜닝하지 않는다.** v1은 RMS를 이미 계산하므로 음성 턴
동안 엔벨로프를 기록해두는 것이 공짜다. **v1이 v2를 결정할 데이터를 스스로
모은다.** 실제 세션이 쌓인 뒤 웃음 구간이 분리되는지 보고, 분리되면 켜고, 아니면
버린다. 숫자는 `MEASURED.md`에 남긴다.

`sulky`와 `curious`는 오디오로 잡히지 않는다. `set_mood`로 가야 하고, 그것은
**CONTRACTS 12 변경 논의를 먼저 여는 것**이 전제다 — 드러내놓고.

## 테스트

- **단위** — 버스: 구독자 0명이면 no-op, level 덮어쓰기(큐 아님), 스냅샷 우선 발행.
  태그 스트리퍼: 태그가 전송 텍스트와 마크다운 양쪽에서 제거되는지, 태그 없을 때
  이벤트가 안 나가는지, 태그처럼 생긴 주인 입력이 mood를 만들지 않는지.
  `speaking` 종료 디바운스 350ms. RMS 엔벨로프의 어택/릴리즈 비대칭.
- **reachability** (`tests/test_reachable.py`) — `/face`와 `/face/stream`에 호출자가
  있는지, `FaceState`/`MoodEvent`를 무언가가 구성하는지.
- **acceptance** (`tests/test_acceptance.py`) — 대화 한 턴을 실제로 굴려서 SSE에
  `thinking → speaking → idle`이 순서대로 나오는지, mood 태그가 이벤트가 되고
  마크다운에는 없는지.
- **직접 돌려본다** — pytest는 동작의 증명이 아니다. 클립을 넣고 `daemon face`를
  열어 음성 대화를 한 번 하고, 검은 프레임·입 지연·전환 이음매를 눈으로 본다.
  이 기능은 "느낌"이 요구사항이라 자동 검증이 구조적으로 닿지 않는다.

## 열린 질문 (계획 단계에서 정할 것)

1. `/face`가 admin과 같은 포트를 쓰는가, 별도 포트인가. (같은 포트를 기본으로 본다)
2. `working`을 v1에 넣는가, `thinking` 폴백으로 두는가. 툴이 도는 시간이 대개
   짧아 표정이 깜빡일 위험이 있다 — 디바운스가 필요한지 실측 후 결정.
3. mood 태그의 정확한 표기와, 모델이 그것을 안정적으로 붙이는지. 붙이지 않으면
   §5의 상황이 텍스트 경로에도 온다 — 계획 단계에서 실제 프로바이더로 확인할 것.
4. `daemon face` CLI가 창 크기·위치·항상 위를 어디까지 제어하는가. (v1은 열기만)
