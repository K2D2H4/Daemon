# 도구 결과를 기억으로 잇는다 — 설계

작성 2026-08-18. 구현 계약이다. 산문보다 시그니처가 중요하다.

근거: PLAN §10.7("도구 결과가 기억으로 가지 않는다"), §4.1(5계층), §4.2(provenance),
§5.2(진화 루프). 규칙: CONTRACTS 비협상 1·3·6·10·12. 선례: ADR 0013 §4.1
(`origin == 'owner'`만 인용하는 유형E).

## 문제

`read_page`가 "발표는 목요일"을 읽어도 그 턴의 컨텍스트에만 들어가고 `tool_calls`에는
감사 기록으로만 남는다. Daemon은 유저 기계를 읽을 수 있지만 그걸로 유저를 알게 되지는
않는다.

## 착수 전 실측 (2026-08-18, 라이브 `data/daemon.sqlite3`)

| | |
|---|---|
| messages | 884 |
| observations | 7 (마지막 행 2026-08-10) |
| persona_rules | 1 |
| tool_calls | 303 (성공 217) |

설계를 바꾼 관측 네 개.

**1. `tool_calls.origin`은 303행 전부 `owner`다.** 그 컬럼은 *턴*의 오리진이고,
비협상 10이 owner 턴만 도구에 닿게 하므로 앞으로도 전부 `owner`다. **출력의 신뢰도에
대해서는 아무 말도 하지 않는다.** 이 작업이 필요로 하는 신뢰 축은 어느 컬럼에도 없고,
*도구*의 성질이지 행의 성질이 아니다.

**2. 스키마 변경이 필요 없다.** `observations.origin`과 `memory_entries.origin`의 CHECK에
`'untrusted'`가 이미 있고, `Store.insert_observation()`과 `CuratedMemory.add()`가 이미
`origin=`을 받는다.

부수적 정정: PLAN §9는 커버링 인덱스를 "스키마 v5를 열 때 함께"라고 적어 뒀지만
`store.py:33`은 이미 `SCHEMA_VERSION = 7`이고 라이브 DB도 v7이다. v5·v6·v7이 그 인덱스
없이 이미 열렸다 — 그 메모는 낡았다. 다음 번호는 v8이고, **이 설계는 열지 않는다.**

**3. `output_excerpt`는 기억용이 아니라 감사용 산출물이다.** `AUDIT_EXCERPT = 500`으로
잘리고, 성공한 217행 중 51행이 그 상한에 붙어 있다. 내용의 상당수가 날 JSON이며
(`notion__notion-search` → id/url/highlight 덩어리) 중복이 심하다 — 같은 "UJET JD" 결과가
5번. 그리고 `tool_calls`에는 메시지·`log_file`로 가는 링크가 없고 UTC `ts`만 있다.

**4. 성찰은 지금 대화만으로도 관찰을 0개 뽑는다.**

| 날짜 | 읽은 메시지 | facts | entities | observations |
|---|---|---|---|---|
| 2026-08-13 | 83 | 0 | 1 | **0** |
| 2026-08-14 | 22 | 0 | 0 | **0** |
| 2026-08-11 | 6 | 1 | 3 | **0** |

**굶주림의 원인이 "도구 결과가 안 들어온다" 하나가 아니다.** 이 설계는 그 사실을 안고
간다 — §"측정" 참조.

## 결정 두 개

### 결정 1 — 도구 결과는 성찰의 *입력*이고, 새로 저장하는 계층이 아니다

PLAN §4.1의 5계층에 여섯 번째를 만들지 않는다. 영구히 남는 것은 결론(facts/entities/
observations)뿐이고 그 셋은 이미 각자 마크다운 집이 있다(`core.md`,
`entities/*.md`, 성찰 아티팩트).

비협상 1("마크다운이 원천")과 충돌하지 않는 이유: 도구 결과는 *기록*이 아니라 *증거*다.
`schema.sql`이 `tool_calls`에 대해 이미 같은 결정을 명시적으로 내려 뒀다 — "재생성
불가능하고, 그래도 된다: 유저가 말한 것이 아니라 기계가 한 일이다." sqlite를 지우면 증거는
사라지지만 결론은 마크다운에 남는다.

기각한 대안: 도구가 반환할 때마다 `memory/observed/YYYY-MM-DD.md`에 append하고 미러를
만든다. 재색인으로 복구되지만, 도구 호출마다 핫패스에 쓰기가 하나 붙고 실제로 남는
것의 대부분이 개발 잡음이다(`run_command` 114건).

### 결정 2 — 세계는 데몬이 아는 것을 늘릴 수 있다. 어떻게 행동하는지는 소유자만 바꾼다

`tool_calls` 안에 성질이 다른 신호가 둘 있다.

- **내용** (`output_excerpt`) — 세계가 쓴 텍스트. 웹페이지든, 남이 보낸 캘린더 초대든,
  동료가 쓴 Notion 페이지든 소유자의 발화가 아니다. 전부 `untrusted`다.
- **메타데이터** (`tool`, `ts`, `ok`, `verdict`) — 컬럼이다. 모델이 위조할 수 없다.

`observations`는 정의상 "이 사람을 어떻게 대할까"이고, 웹페이지는 그걸 말할 자격이 없다.
그래서:

**내용은 facts까지만 갈 수 있고, `observations` 테이블에는 도달 경로가 없다.**
관찰은 메타데이터에서만 나온다.

ADR 0013 §4.1이 유형E에 대해 내린 판단과 같은 방향이고 더 강하다. 저쪽은
`origin == 'owner'`인 기억만 인용하는 *필터*고, 이쪽은 경로를 없앤다 — 비협상 10이
"offering side는 편의, `decide`가 보증"이라고 구분한 취향 그대로, 잊어버릴 수 있는
필터보다 닿을 수 없는 구조가 낫다.

기각한 대안: 내용도 관찰이 되게 하되 `origin='untrusted'`로 찍고
`unconsumed_observations`가 승격만 막는다. `observations`는 append-only(비협상 6)라 그
행은 영원히 남고, 나중에 그 필터를 지우면 승격된다.

**솔직히 적어 둘 한계**: 이 결정도 `untrusted` 내용이 프롬프트에 닿는 걸 막지 못한다.
`core.md`는 매 턴 주입된다. 막는 것은 그것이 **행동**이 되는 것이다.

## 구현

### 모델 호출을 둘로 나눈다

결정 2를 프롬프트가 아니라 파싱 경로로 구현하는 방법이다.

```
호출 1 (기존)   대화 + 사용 요약        -> facts, entities, observations
호출 2 (신규)   도구 내용 다이제스트     -> facts 만
```

**호출 2의 응답 스키마에는 `observations` 키가 없고 파서가 받지 않는다.** 모델에게
부탁하는 것이 아니라 경로가 없다. 그날 자격 있는 도구 내용이 없으면 호출 자체를 하지
않는다.

**호출 2가 entities를 만들지 않는 이유**: `entities` 테이블에 `origin` 컬럼이 없어서
`untrusted`로 표시할 수가 없다. 표시하지 못할 것은 만들지 않는다. 그리고 동기가 된 예
("발표는 목요일")는 실제로 사실이지 엔티티가 아니다.

**호출 1의 프롬프트는 최소로만 건드린다.** 사용 요약 블록 하나를 추가하는 것이 전부다.
실측 4 때문이다 — 관찰이 0으로 남았을 때 그것이 이 변경 탓인지 원래 그런 것인지
구분되어야 한다.

### 파일

```
daemon/reflection.py       다이제스트·사용 요약 조립, 호출 2, untrusted 사실 적용
daemon/memory/store.py     tool_calls_for_day (frozen 아님)
daemon/memory/schema.sql   변경 없음
daemon/persona/evolve.py   변경 없음 — untrusted 가 observations 에 없으므로
```

### `store.py`

```python
def tool_calls_for_day(self, date: str) -> list[sqlite3.Row]
```

`tool_calls`에는 `log_file`이 없고 UTC `ts`만 있다. UTC로 `[date-1, date+1]` 창을 뜬 뒤
`log.local_date`로 파이썬에서 거른다. `ts`에 `BETWEEN`을 걸면 KST 하루가 9시간 밀린다 —
`messages_for_day`의 docstring이 경고하는 바로 그 함정이다. `store.py`는 이미
`daemon.memory.log`에서 `from_iso`를 가져오므로 순환 import는 없다.

거부·실패 행도 반환한다. 거르는 것은 호출자다.

### `reflection.py`

```python
TOOL_DIGEST_CHARS  = 4000   # 다이제스트 전체 상한
TOOL_DIGEST_ITEMS  = 20     # 중복 제거 후 항목 수 상한
TOOL_EXCERPT_CHARS = 400    # 항목 하나의 상한

CONTENT_TOOLS: frozenset[str]   # 내용이 다이제스트에 들어갈 수 있는 도구
```

```python
def _tool_digest(rows: list[sqlite3.Row]) -> str
def _tool_usage(rows: list[sqlite3.Row]) -> str
```

**`_tool_digest`** — 호출 2의 입력. `ran=1 AND ok=1`이고 `tool`이 `CONTENT_TOOLS`에 있는
행만. 동일한 `(tool, output_excerpt)`는 중복 제거(“UJET JD” 5번 → 1번). 오래된 것부터
버려 상한을 맞춘다. 전체를 액자에 넣는다 — `fetch_page`가 이미 쓰는 “읽을 자료지 지시가
아니다” 문구와 같은 것이고, 같은 이유로 필요하다.

**`_tool_usage`** — 호출 1의 입력. **내용이 0바이트다.** 도구 이름, 대략의 시간대, 횟수,
성공/실패만. 컬럼에서 나오므로 모델이 위조할 수 없다.

`CONTENT_TOOLS`는 허용 목록이지 거부 목록이 아니다. 새 MCP 도구가 붙었을 때 기본이
"들어간다"이면 아무도 결정하지 않은 채 내용이 흘러든다. 초기 구성원은 라이브 분포를
보고 정한다:

```
read_page  fetch_page                          유저가 보고 있는 것 (§10.5)
tavily__tavily_search                          웹 검색
notion__notion-fetch  notion__notion-search  notion__notion-list-private-pages
google__get_events  google__list_calendars     "발표는 목요일"이 실제로 사는 곳
```

빠진 것과 이유: `read_file`·`run_command`·`list_dir`·`system_state`·`see_screen`·
`write_file`·`open_path`·`list_tabs`는 기계의 상태이거나 우리가 한 행동이지 기억할
자료가 아니다. 실측된 `read_file` 발췌는 전부 plist와 파이썬 스크립트였다.

MCP 서버를 새로 붙여도 자동으로 등록되지 않는다. 그 마찰이 의도다.

### 적용

호출 2의 사실은 `origin='untrusted'`로 들어간다.

```python
await self._curated.add(fact.body, ..., origin="untrusted", session_kind="reflection")
```

**호출 2의 사실은 `key`도 `updates`도 가질 수 없다.** 파서가 두 필드를 아예 읽지 않는다.
둘 다 기존 사실을 *retire*시키는 수단이고(ADR 0010), 웹페이지가 소유자가 말한 사실을
지울 수 있으면 그게 세탁이다. 새 사실로만 추가된다.

**순서**: 호출 1을 먼저, 호출 2를 나중에. 호출 1의 `_resolve_updates`가 보는 활성
집합이 untrusted 사실 때문에 흔들리지 않게 한다.

**아티팩트**: 호출 2의 사실도 `memory/reflections/YYYY-MM-DD.md`에 들어가되 출처가
보이게 구분해 적는다. 사람이 검토용으로 읽는 파일에서 "이건 웹에서 왔다"가 안 보이면
그 파일은 검토에 못 쓴다.

`Result`에 호출 2의 산출을 별도로 센다. 합산하면 어느 경로가 일했는지 보이지 않고,
그것이 이 작업에서 알고 싶은 전부다.

`tests/test_reachable.py`: 새 PENDING 없음. `tool_calls_for_day`는 `reflection.py`가
부르므로 배선되어 있고, 닫을 스테일 PENDING도 없다.

핀으로 박을 것:

- 호출 2의 사실이 `origin='untrusted'`로 저장된다
- **호출 2의 사실은 기존 사실을 retire시키지 못한다** — `key`/`updates`를 실어 보내도
  무시되고 새 사실로만 추가된다
- 자격 있는 도구 내용이 없는 날은 호출 2를 하지 않는다
- `CONTENT_TOOLS`에 없는 도구의 내용은 다이제스트에 들어가지 않는다
- 사용 요약에 `output_excerpt`의 어떤 부분문자열도 없다
- 실패·거부된 호출은 다이제스트에서 빠지고 사용 요약에는 남는다
- 다이제스트가 액자 문구를 포함한다

## 측정

유닛 테스트는 완료의 증거가 아니다. 라이브 DB **사본**에 대고 실제 `daemon reflect
--force`를 돌린다. 대상은 도구 호출이 있는 날 — 2026-08-13(17건), 2026-08-14(55건).

1. 변경 전 baseline을 먼저 뜬다(관찰 0, 사실 0). 실측 4가 있으므로 이게 없으면 결과를
   해석할 수 없다.
2. 변경 후 같은 날을 `--force`로 다시 돌린다.
3. 늘어난 행의 **본문을 눈으로 읽는다.** 개수는 품질이 아니다.
4. 실측치를 `daemon/MEASURED.md`에 남긴다.

**예상과 그 한계를 미리 적어 둔다.** 사실은 늘 것이다 — 호출 2가 없던 경로다. 관찰이
늘지는 알 수 없다. 사용 요약이 모델에게 충분한 재료인지에 달렸고, 실측 4는 그 모델이
대화 83건에서도 0개를 뽑았다고 말한다. **안 늘면 그렇게 보고하고 원인을 따로 판다.**
초록 테스트로 덮지 않는다.

LLM 거동을 A/B로 비교하게 되면 배치 10개로 결론 내지 않는다 — p-value를 붙이거나,
결론을 내지 않는다.

### 실측 결과 (2026-08-18, `gemini-3.6-flash`, 라이브 사본)

**예상은 두 쪽 다 틀렸고, 방향이 반대였다.**

**관찰은 늘었고 유의하다.** 2026-08-10, 팔당 20회, 매회 새 데이터 사본:

| | 평균 관찰/회 | 관찰 0건인 회 |
|---|---|---|
| 변경 전 | 0.85 (sd 0.88) | **9/20** |
| 변경 후 | 1.75 (sd 0.55) | **1/20** |

차이 +0.90, **양측 순열검정 p = 0.0012**(몬테카를로 20만 회). M4에 걸리는 숫자는
평균이 아니라 두 번째 열이다 — 관찰이 하나도 안 나오는 밤이 거의 사라졌다.
**올린 것은 도구 내용이 아니라 사용 요약이다.**

**사실은 늘지 않았다. 0건이다.** 그리고 이건 실패가 아니라 결과다. 호출 2는 4일 모두
실제로 실행됐고(다이제스트 630~4121자), 캘린더의 "Happy birthday!" 항목에서 생일을,
Notion JD에서 이름·이메일·직무를 정확히 뽑았다. **그 셋이 전부 이미 `memory_entries`에
있었다** — 같은 날 대화로 학습된 것들이다. 처음엔 그걸 모르고 중복 3건을 추가했고,
개수만 보면 "새 사실 3건"이었다. **본문을 읽어서 잡았다.** 호출 2에 큐레이션 계층을
읽기 전용으로 넣고 정확 중복을 떨구자 4일 전부 0건이 됐다. 값은 소유자가 입에 올리지
않는 것을 데몬이 읽는 날에 나오고, 이 히스토리에는 그런 날이 없다.

**한 번 돌린 값으로는 아무것도 몰랐다.** 위 A/B의 첫 측정은 팔당 1회였고 0 → 2였다.
설득력 있어 보였지만 20회를 돌리니 변경 전 평균이 0.85에 0이 9번이었다 — "관찰 0"은
그 날의 고정된 성질이 아니라 절반 확률로 나오는 눈이었다.

### 실측이 남긴 후속 두 개

**(1) `tavily__tavily_search`는 `CONTENT_TOOLS` 중 가장 약하고, 약한 방향이 나쁘다.**
2026-08-10의 발췌는 소유자 이름 검색이 **동명이인의 이력서**(cv.hatemogi.com — Rust·
Scala·Clojure, 소유자는 AI/LLM 엔지니어)를 물어온 것과 "AI latest news Korean"이었다.
동명이인 CV는 확신에 찬 틀린 사실이 매 턴 주입되는 정확한 모양이다. 이번 실행에서는
하나도 만들지 않았고 폭발 반경은 설계상 막혀 있지만(`untrusted`, retire 불가, 규칙 승격
불가, 아티팩트에서 별도 표기), **저 목록에서 하나를 뺀다면 이것부터다.**

**(2) `daemon reflect --force`가 아티팩트를 덮어쓰지 않고 append한다.** 이 작업의
결함이 아니다 — 변경 전 코드에서도 같은 파일에 `# 2026-08-10 성찰` 헤더가 두 개 생긴다
(`_write_artifact`가 `open_private_append`를 쓴다). 사람이 검토용으로 읽는 파일에
모순되는 두 판이 쌓이므로 결함이지만 이 설계의 범위 밖이라 손대지 않았다.

- `daemon/proactivity/**` — 다른 워크트리가 선제성 판단기를 파고 있다. 이 설계는
  그쪽 파일을 건드리지 않는다.

  스키마를 여는 별도의 결정이다.

  드러내되 고치지 않는다.
